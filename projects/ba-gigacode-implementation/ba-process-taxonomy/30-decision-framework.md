# Как выбрать процесс, объявить новый и построить маршрут

## 1. Выбор процесса по входу и цели

Процесс определяется парой «класс входного артефакта + требуемый целевой
выход», а не темой задачи. Порядок проверки — сверху вниз, первое совпадение
выигрывает.

| Шаг | Вопрос | Да → |
| --- | --- | --- |
| 1 | Вход — внешний документ, обязательства по которому ещё не приняты? | `P-08` `tender-tz-assessment` |
| 2 | Вход — сырая запись, письмо, заявка от источника внутри компании? | `P-01` `elicitation-processing` |
| 3 | Ядро требований содержит неразрешённые неоднозначности выше порога? | `P-02` `clarification-management` |
| 4 | Нужно обоснование изменения для решения «делаем / не делаем»? | `P-03` `bcreq-formation` |
| 5 | Решение принято, нужны требования к функциям для разработки? | `P-04` `fr-detailing` |
| 6 | Нужен документ-договор по внешнему эталону структуры? | `P-05` `tz-composition` |
| 7 | Нужна модель поведения: акторы, сценарии, потоки? | `P-06` `scenario-modeling` |
| 8 | Нужен вердикт о качестве готового документа? | `P-07` `requirements-verification` |
| 9 | Пришло изменение к уже зафиксированным требованиям? | `P-09` `change-impact-assessment` |
| 10 | Нужно зафиксировать состояние, след или базис версии? | `P-10` `requirements-lifecycle-management` |

**Если ни один шаг не сработал.** Это отказ на входе (`T-1`), а не повод
назвать работу свободным текстом. Отказ оформляется задачей на расширение
словаря с описанием непокрытого случая (`T-2`). Именно этот запрет закрывает
дефект `D7`: 66 значений процесса из 67 были свободным текстом.

## 2. Процесс, навык или операция: тест уровня

| Признак | Процесс `L2` | Навык `L3` | Операция |
| --- | --- | --- | --- |
| Целевой выход | документ или модель, живущие вне маршрута | промежуточный результат, предъявимый гейту | элемент артефакта |
| Гейт | завершающий гейт обязателен | собственный гейт обязателен | гейта нет, есть контракт выхода |
| Ветвление | между навыками | внутри навыка допускается | запрещено (`OA-2`) |
| Состояние ЖЦ | меняет состояние целевого артефакта | не меняет | не меняет |
| Единица компиляции | маршрут | `SKILL.md` | шаг внутри `SKILL.md` |

Различающий вопрос при сомнении: **что предъявляется по завершении и кому**.
Если результат предъявляется человеку и меняет состояние документа — процесс.
Если результат предъявляется следующему шагу и проверяется гейтом — навык.
Если результат — элемент, у которого есть контракт формы, но нет отдельной
проверки, — операция
([`ba-operation-taxonomy/30-decision-framework.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/projects/ba-gigacode-implementation/ba-operation-taxonomy/30-decision-framework.md), §1).

## 3. Маршрут: граф, а не список

Маршрут процесса объявляется как граф (`RG-1`): вершины — навыки, рёбра —
переходы с условием. Условие вычисляется гейтом предыдущей вершины.

```text
P-01 elicitation-processing
  SK-transcript-normalization
        │ выход схемы валиден
        ▼
  SK-context-extraction
        │
        ▼
  SK-ambiguity-detection ──── неоднозначностей выше порога > 0 ──▶ P-02
        │                                                          │
        │ неоднозначностей нет                    ответы получены   │
        ▼                                                          ▼
  SK-core-assembly ◀────────────────────────── SK-answer-integration
        │ A-CORE прошёл G-mach
        ▼
      выход: A-CORE validated
```

| Правило маршрута | Формулировка |
| --- | --- |
| `RT-1` | Каждое ребро имеет условие, вычислимое из результата гейта или из объявленного поля артефакта. Ребро без условия допустимо только при единственном исходящем ребре. |
| `RT-2` | Из каждой вершины существует ребро отказа: маршрут, не имеющий выхода при непройденном гейте, останавливается тупиком (нарушение `GT-2` «fail-closed» превращается в зависание). |
| `RT-3` | Переход между процессами (`P-01 → P-02`) объявляется в графе явно; неявная передача работы «в другой процесс» запрещена, так как разрывает след. |
| `RT-4` | Цикл объявляет предел итераций и действие при его достижении (`RG-5`). Для `P-02` предел по умолчанию — две итерации уточнения, далее эскалация человеку. |
| `RT-5` | Прогон записывает пройденную траекторию в `A-TRACE`; траектория, не восстановимая по следу, считается непроведённым прогоном. |

**Что здесь изменилось по сравнению с действующей мета-моделью.** Формулировка
«маршрут неизменен внутри прогона» сохраняется по смыслу и уточняется по форме:
неизменен **граф**, а не траектория. Выбор ветви — исполнение (`RG-3`);
изменение множества вершин, рёбер или условий — новая версия маршрута между
прогонами (`RG-4`).

## 4. Привязка гейтов: три исполнителя и семь ярусов

Мета-модель различает гейты по исполнителю: `G-self` (агент проверяет себя),
`G-mach` (валидатор), `G-human` (человек). Модуль AI-образования различает
механизмы контроля по тому, кто исполняет правило (`G1`–`G7`). Это две
ортогональные оси, и их следует соединить явно, а не выбирать одну.

| Исполнитель гейта | Ярусы `G1`–`G7` | Что этим удерживается |
| --- | --- | --- |
| `G-self` | `G1` (текст в промпте), `G2` (схема вывода) | форма результата, полнота обязательных полей |
| `G-mach` | `G2`, `G3` (контракт инструмента), `G6` (внешний верификатор) | схема артефакта, закрытые словари, наличие ссылок на источник, покрытие |
| `G-human` | `G5` (HITL) | смысл, продуктовое решение, приёмка, принятие риска |

| Правило | Формулировка |
| --- | --- |
| `GB-1` | Ярус выбирается по обратимости действия, а не по важности задачи (`AE-2`, `AE-3`). |
| `GB-2` | Человеческий гейт не подменяется автоматическим: переход `A-BCREQ` в `approved`, отправка вопросов Заказчику и фиксация базиса версии удерживаются `G5`. |
| `GB-3` | Гранулярность гейта объявляется: задача целиком, класс инструментов, предикат по аргументам или класс эффекта. По умолчанию — **класс эффекта**: прерываются действия, объявленные необратимыми. |
| `GB-4` | Машинный гейт `G6` обязан быть детерминированным: его критерий вычисляется без обращения к модели. Проверка «есть ли у элемента ссылка на источник» детерминирована; проверка «хорошо ли сформулировано» — нет и на `G6` не выносится. |
| `GB-5` | Машинный гейт выражается командой оболочки: среда исполнения даёт агенту сборку, тесты и линтеры (`GC-11`), поэтому `G-mach` исполним внутри прогона, а не только в CI. Проверка, опирающаяся на `curl` или `wget`, гейтом быть не может — эти команды запрещены профилем прав среды (`GC-12`); внешние данные берутся через MCP-инструмент. Факты — [снимок документации среды](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/2026-09-10-gigacode-environment-facts.md). |

### 4.1. Контракт человеческого гейта: прослеживаемость источника

Человеческий гейт дорог и необратим, поэтому предъявляемый ему материал обязан
быть проверяемым без повторного чтения всего входа.

| Требование | Формулировка |
| --- | --- |
| `HGC-1` | Каждое утверждение, выносимое на человеческий гейт, сопровождается ссылкой на источник в форме сноски: документ, раздел, страница или тайм-код, дословная цитата. |
| `HGC-2` | Утверждение без ссылки на источник помечается как гипотеза исполнителя и предъявляется отдельным перечнем, а не смешивается с утверждениями, имеющими основание. |
| `HGC-3` | Ссылка проверяема машинно на **наличие и разрешимость** (`check-source-evidence`), человеком — на соответствие цитаты смыслу утверждения. Первое — `G6`, второе — `G5`. |
| `HGC-5` | Технический мерж или approve pull request **не является** прохождением `G-human`: это процедурный шаг конфигурационного управления. Содержательный `G-human` требует явного вердикта ревьюера, зафиксированного отдельно от статуса ветки. |
| `HGC-6` | Вердикт содержит: перечень фактически прочитанных документов и артефактов, решение (`принято` / `принято с условиями` / `отклонено`), основание решения и подпись ревьюера с датой. Отсутствие любого элемента означает, что гейт не пройден (`GT-2`, fail-closed). |
| `HGC-7` | Разделение проверяемо: у артефакта, прошедшего `G-human`, есть вердикт `HGC-6`; отсутствие вердикта при наличии мержа — дефект, а не основание считать гейт пройденным. |
| `HGC-4` | Доля утверждений с валидной ссылкой измеряется как `provenance coverage` = принятые утверждения со ссылкой / все принятые утверждения ([`research/ai-education/evaluation/20-taxonomy.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ai-education/evaluation/20-taxonomy.md)). |

Правила `HGC-5`–`HGC-7` записаны по ответу владельца в
[комментарии к PR #572](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/pull/572):
approve pull request подтверждает лишь процедурную готовность изменения, тогда
как содержательный `G-human` означает **сознательное изучение** документации и
артефактов ревьюером с явным выводом. Разделение существенно потому, что
approve дёшев и производится по объёму диффа, а вердикт `HGC-6` называет
прочитанное поимённо и потому проверяем.

Требование `HGC-1` не является изобретением Хаба: та же норма действует в среде
исполнения, где проверка перехода к решению формулируется как «каждое
утверждение подтверждено файлом и строкой», а проверка результата — как
«проверка выполнена и показана, а не заявлена словами» (`GC-14`, `GC-15`,
[снимок документации среды](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/2026-09-10-gigacode-environment-facts.md)).
Совпадение снижает стоимость дельты: правило не придётся навязывать
исполнителю дополнительно.

## 5. Контракт исполнимости процесса агентом

Процесс считается исполнимым агентом, если выполнены шесть условий. Проверка
машинная там, где это указано.

| Условие | Формулировка | Проверка |
| --- | --- | --- |
| `EX-1` | Вход объявлен классом артефакта и состоянием ЖЦ | машинная |
| `EX-2` | Целевой выход единственный и имеет схему | машинная |
| `EX-3` | Каждый навык имеет вход, выход и ярус гейта | машинная |
| `EX-4` | Каждый навык разложен на операции закрытого словаря | машинная |
| `EX-5` | Граф маршрута связен: из входа достижим выход, из каждой вершины есть ребро отказа | машинная |
| `EX-6` | Необратимые действия удерживаются `G5` | ревью |

Процесс, не удовлетворяющий `EX-1`–`EX-5`, не запускается автоматически:
он исполняется человеком и помечается `Actor=human` (`AE-4`). Пометка — не
поражение модели, а честное объявление границы автоматизации.
