Руководство оператора MVP BCREQ

Как запустить маршрут RG-BCREQ-v1, продолжить его в новой сессии, проверить результат и безопасно подготовить публикацию в Confluence.

TASK-rooted state fail-closed human in control

1. Статус документа

Hub execution package · RFC proposed Руководство относится к копируемому модулю execution-package-gigacode-cli/ в Хабе. Оно не утверждает, что пакет уже перенесён во внешний runtime mango-ba-ai-runtime-cli: такой перенос остаётся отдельным решением и отдельным PR.

Архитектурное основание — RFC развёртывания MVP. Целевой продукт — GigaCode CLI на локальной рабочей станции, не VS Code extension и не hosted AI-session GitVerse.

2. Установка и preflight

  1. Установите CLI через канал вашей организации по официальному quick start. Не копируйте токены или внутренние URL в репозиторий.
  2. Скопируйте execution-package-gigacode-cli/ в чистый каталог спутника, добавьте утверждённые срезы в meta-model/ и локальные материалы в docs/kb/, затем перейдите в корень пакета и проверьте CLI: 
    cd <каталог-спутника>
gigacode --version
  3. Проверьте пакет до запуска агента: 
    sh tools/validate-package.sh
    Успех — код возврата 0. Любой иной код означает stop; validator не должен сам изменять package или результат. Разрешён только append-only audit event о reject.
  4. Запустите CLI из корня проекта: 
    gigacode
  5. Внутри CLI проверьте контур: 
    /memory
/skills
/mcp
    В списке skills должен быть rg-bcreq-v1-dispatcher. В памяти — project contract. Для дополняющего поиска в корпоративной БЗ должен быть доступен одобренный MCP с read/search capabilities.
Если диспетчера нет Перезапустите CLI после обновления проекта и проверьте файл .gigacode/skills/rg-bcreq-v1-dispatcher/SKILL.md. Старый путь .agents/skills/ не считается CLI-установкой.

3. Запуск задачи

Подготовьте уникальный ID формата TASK-0001, затем:

  1. Явно вызовите диспетчер: 
    /skills rg-bcreq-v1-dispatcher
  2. На запрос диспетчера передайте только TASK ID и предметный вход: 
    TASK-0001
Подготовь BCREQ для …
  3. Проверьте показанный preflight: TASK_ID, route, найденный/создаваемый каталог, первый узел и доступность источников.
  4. Подтвердите начало. После этого источником состояния становится runs/TASK-0001/, а не история чата.

Ожидаемая структура:

runs/TASK-0001/
├── task.yaml
├── runs/RUN-0001.yaml
├── evidence/
├── A-BCREQ.md
└── A-BCREQ.confluence.html
Не запускайте маршрут обычной фразой Автоматический выбор model-invoked skill удобен для справочных задач, но не доказывает порядок узлов RG-BCREQ-v1. Строгий маршрут начинается только явным вызовом диспетчера.

4. Продолжение в новой сессии

Команда /resume удобна, но не обязательна. Если сессия закрыта или контекст потерян, запустите GigaCode CLI из того же checkout, снова вызовите dispatcher и передайте прежний TASK_ID.

  1. Dispatcher читает task.yaml.
  2. Проверяет единственный active_run_id и последовательность events.
  3. Показывает последний принятый gate и вычисленный следующий узел.
  4. Продолжает только после вашего подтверждения.

Не создавайте второй TASK для продолжения той же предметной задачи. Новый RUN_ID внутри TASK разрешён только после решения restart; старый run record сохраняется.

5. Локальная БЗ и Confluence

ST-LOCAL

Dispatcher ищет версионируемые знания в docs/kb/ и сохраняет ссылки на найденные файлы.

ST-CONFLUENCE

Параллельно используется разрешённый MCP read/search: корпоративная БЗ дополняет локальный контекст, а не служит запасным уровнем.

До использования найденного факта человек подтверждает название, раздел, страницу или anchor, короткую цитату и ссылку. Для Confluence event также хранит server alias, поисковый запрос, page ID/URL и время чтения. Секреты и полный кэш страницы не должны попадать в runs/. Если MCP отсутствует, отключён или не объявляет нужную capability, маршрут останавливается у человека.

Два дополняющих канала Достаточность локального ответа не отменяет поиск в Confluence. Недоступность одного канала фиксируется явно и передаётся человеку; web-поиск не является скрытым третьим уровнем источников.

6. Если validator вернул reject

Ожидаемый сценарий:

  1. Команда завершается ненулевым кодом.
  2. В RUN добавляется append-only reject event.
  3. На экране показаны invariant, файл/поле, ожидание и команда recheck.
  4. Ни один проверяемый файл автоматически не исправляется; единственная допустимая запись — новый reject event.
  5. Вы выбираете manual-fix, restart или cancel.
sh tools/validate-package.sh --task TASK-0001
Reject нельзя подтвердить как success Сначала устраните причину вручную либо явно начните новую попытку. Увеличение числа автокоррекций не является допустимым обходом.

7. Human checkpoints

CheckpointЧто показывает dispatcherЧто решает человек
Возражение Конфликт, варианты и рекомендацию до спорного действия Изменить путь, продолжить допустимый вариант или остановить
Полнота Матрицу «критерий → evidence → секция» и смежные улучшения отдельно Закрыть пробел; не расширять scope; создать отдельную задачу
Двойное подтверждение Target, page ID, representation, preview/diff и fingerprint Сначала intent, затем тот же fingerprint непосредственно перед write

Любое изменение target или содержимого аннулирует подтверждения. Локальная запись нового результата обратима и не требует двойного подтверждения; внешняя публикация или перезапись страницы требует.

8. Экспорт и публикация в Confluence

A-BCREQ.md — канонический редактируемый source. A-BCREQ.confluence.html — безопасный XHTML/HTML fragment для Confluence Storage Format: без JavaScript, inline handlers, credentials и локальных абсолютных путей.

  1. Запустите validation и проверьте принятый финальный gate.
  2. Откройте export локально и проверьте заголовки, таблицы, ссылки и anchors.
  3. Попросите dispatcher подготовить publish preview, но не выполнять write.
  4. Сверьте page ID/URL, representation и diff; дайте первое подтверждение.
  5. Непосредственно перед MCP write подтвердите неизменившийся fingerprint второй раз.
  6. Сохраните page ID, version и content_sha256 в event.
Идемпотентная публикация Повтор для той же пары TASK_ID + content_sha256 не должен создавать дубликат. Если MCP принимает ADF или Markdown вместо storage, representation и преобразование фиксируются явно.

9. Как добавить хороший пример в Golden Set

  1. Выберите TASK с финальным accepted gate и проверяемым evidence.
  2. Получите отдельное одобрение использовать его как golden-кандидат.
  3. Удалите персональные данные, секреты и закрытые ссылки.
  4. Создайте новый стабильный case-id; существующие cases не переписывайте.
  5. Запишите origin_task_id, confirmed_by, confirmed_at, класс и обоснование ожидаемого вердикта.
  6. Если пример закрывает новый дефект, добавьте связанный negative case.
  7. Обновите golden/cases.yaml, запустите validator и golden tests.
  8. Передайте изменение на обычный PR review.

Чат, пользовательский run или страница Confluence никогда не становятся golden автоматически. Golden — управляемый test artifact, а не память модели.
