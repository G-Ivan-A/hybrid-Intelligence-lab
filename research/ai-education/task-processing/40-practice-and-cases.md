# Task Processing: практика и кейсы

> **Динамическая ветка модуля.** Версии API, числа вендоров и состав
> фреймворков устаревают за месяцы; объектная модель и точки решений — нет.
> Поэтому этот файл вынесен из [10-theory.md](10-theory.md) и
> [30-decision-framework.md](30-decision-framework.md) и **обязан** ссылаться на
> своё основание в них.
>
> **Класс источников.** Здесь смешаны спецификации (S1), рецензируемые работы
> (S2), препринты (S3) и инженерные отчёты вендоров (S4). Класс указан у каждого
> утверждения, потому что число из отчёта вендора на собственных данных и
> строка спецификации — доказательства разной силы
> ([00-introduction.md](00-introduction.md), «Метод и границы доказательности»).

## 1. Разделение «оркестратор / воркер» в промышленных фреймворках

Проверяемое утверждение раздела: механизм делегирования существует во всех
рассмотренных фреймворках, но **контракт делегирования** — что именно
передаётся воркеру — нигде не формализован. Это подтверждает В1 из
[00-introduction.md](00-introduction.md).

### 1.1. Anthropic: orchestrator-worker в исследовательской системе (S4)

Инженерный отчёт описывает архитектуру, где ведущий агент «анализирует запрос,
вырабатывает стратегию и порождает субагентов, исследующих разные аспекты
параллельно».

Что важно для нашей рамки:

| Наблюдение отчёта | Куда ложится |
| --- | --- |
| Рабочее описание подзадачи требует «an objective, an output format, guidance on the tools and sources to use, and clear task boundaries» | оси класса M1, [20 §1](20-taxonomy.md) |
| Короткие инструкции вида «research the semiconductor shortage» проваливались, будучи «vague enough that subagents misinterpreted the task» | прямое свидетельство для H1: неполнота ≠ компактность |
| Правила масштабирования усилий закладываются в промпт (простой запрос — один агент и 3–10 вызовов; сложный — 10+ субагентов) | ярус G1 применён по назначению: приоритет, а не запрет (H12) |
| Эвристика «сначала осмотри все доступные инструменты» | слой A pre-flight-верификации, [30 §3](30-decision-framework.md) |
| Наблюдавшиеся отказы: порождение 50 субагентов на простой запрос; бесконечный поиск несуществующих источников; выбор неверных инструментов | H8: отсутствие ограничителя перепланирования = отсутствие условия завершения (D9) |
| Агенты расходуют ≈×4 токенов относительно чата; MAS — ≈×15; расход токенов объясняет 80% дисперсии результата | цена мультиагентности, [30 §5](30-decision-framework.md) |
| Конфигурация с ведущим агентом Opus 4 и субагентами Sonnet 4 превзошла одиночного Opus 4 на 90.2% на внутренней оценке | **число вендора на собственных данных**; воспроизведение неизвестно |
| Оценка — LLM-судья по рубрике: фактическая точность, точность цитирования, полнота, качество источников, эффективность инструментов | [30 §4](30-decision-framework.md) |
| Люди находят краевые случаи, которые пропускают автооценки, включая смещения при выборе источников | там же, следствие 2 |
| Продакшн-требование: возобновление с точки отказа вместо перезапуска | предпосылка персистентности для гейтов, [30 §2](30-decision-framework.md) |

### 1.2. CrewAI: `Process.hierarchical` (S1)

Два режима процесса: `sequential` (задачи идут по порядку, выход одной —
вход следующей) и `hierarchical`, требующий параметра `manager_llm` **или**
`manager_agent`. Существенно: в иерархическом режиме менеджер **не назначает
задачи заранее** — он «распределяет задачи агентам исходя из их возможностей,
проверяет результаты и оценивает завершённость».

Это P4 в чистом виде ([20 §2](20-taxonomy.md)): состояние поиска — у
супервизора. Проверка результата встроена в роль менеджера, но менеджер —
такая же модель, поэтому по [20 §2](20-taxonomy.md) это **не** внешняя
верификация (H9): цикл замкнут внутри `Policy`.

### 1.3. AutoGen: handoff как вызов инструмента (S1)

Ключевая идея паттерна — «let agent delegate tasks to other agents using a
special tool call». Коммуникация событийная (pub-sub), с типами сообщений
`UserTask` (несёт историю переписки), `AgentResponse`, `UserLogin`; классы
`AIAgent`, `HumanAgent` (прокси для случаев, требующих человека), `UserAgent`,
`RoutedAgent`. При вызове delegate-инструмента агент публикует `UserTask` в
топик другого агента и **прекращает собственное исполнение**.

Два следствия для рамки:

1. **Делегирование выражено на ярусе G3** — как контракт инструмента, а не как
   текстовое правило. Это делает сам факт передачи наблюдаемым и валидируемым.
2. **Передаётся история переписки**, а не выжимка мандата. Это архитектурный
   выбор в точке D1/RQ7: контекст сохраняется полностью, но границы подзадачи
   при этом явно не переопределяются — что и есть механизм возникновения
   «рассогласования между агентами» (см. §3).

`HumanAgent` показывает, что эскалация к человеку моделируется как **ещё один
адресат делегирования**, а не как особый режим системы.

### 1.4. LangGraph: топология как ограничение (S1)

Граф с супервизор-узлом сочетает P4 и P5: декомпозиция — у модели, множество
допустимых переходов — у топологии, заданной человеком вне модели. Это
единственная из рассмотренных конструкций, где часть ограничений выражена
структурно и потому не подлежит переинтерпретации моделью
([20 §3](20-taxonomy.md), ярус G5–G7 по правам узла).

## 2. Guardrails, сохраняющие инициативу

### 2.1. LangChain / LangGraph: `HumanInTheLoopMiddleware` (S1)

Механизм: middleware «lets you add human oversight to agent tool calls»; при
попадании вызова под политику «the middleware issues an interrupt that halts
execution», а «the graph state is saved using LangGraph's persistence layer, so
execution can pause safely and resume later».

Четыре исхода решения человека:

| Исход | Что делает |
| --- | --- |
| `approve` | «Execute the tool with the original arguments as proposed by the agent» |
| `edit` | «Modify the tool arguments before execution» |
| `reject` | «Skip executing this tool call entirely and return rejection feedback» |
| `respond` | «Return the human's message directly as a synthetic tool result» |

Конфигурация: `interrupt_on` — «Mapping of tool names to approval configs.
Values can be `True` (interrupt with default config), `False` (auto-approve)»;
дополнительно предикат `when` позволяет прерывать выборочно по аргументам
вызова. Обязательное условие: «You must configure a checkpointer to persist the
graph state across interrupts».

**Почему это ключевой кейс модуля.** Здесь одновременно выполнены все три
свойства «гейта, совместимого с инициативой» из
[30 §2](30-decision-framework.md):

1. гранулярность — по имени инструмента и по предикату на аргументах, а не по
   задаче (строки 2–3 таблицы в [20 §3.1](20-taxonomy.md));
2. исходов больше двух: `edit` и `respond` дают исполнителю легальный выход
   вместо выбора «нарушить или встать» (H13);
3. состояние персистентно, исполнение возобновляемо — гейт не стоит потерянной
   работы.

Это и есть промышленный аналог «двухфакторного подтверждения» из постановки
#457: не запрет менять структуру, а **прерывание на классе действий с правом
человека отредактировать аргументы**.

### 2.2. OpenAI Agents SDK: guardrails и tripwires (S1)

Гардрейлы «enable you to do checks and validations of user input and agent
output». Функция гардрейла возвращает `GuardrailFunctionOutput` с булевым
`tripwire_triggered`; при `true` SDK немедленно возбуждает исключение
(`InputGuardrailTripwireTriggered` / `OutputGuardrailTripwireTriggered`) и
исполнение останавливается.

Размещение зафиксировано в спецификации: входные гардрейлы исполняются только
на **первом** агенте («intended to run on user input»), выходные — только на
**последнем** («the final agent output»). Мотивировка — «guardrails tend to be
related to the actual Agent… so colocating the code is useful for readability».
Входные гардрейлы поддерживают два режима: параллельный (по умолчанию, лучше
латентность) и блокирующий — он «prevents token consumption if triggered».

**Куда это ложится.** Это ярус G4 ([20 §3](20-taxonomy.md)) и слой B
pre-flight-верификации ([30 §3](30-decision-framework.md)): блокирующий входной
гардрейл — единственный из просмотренных механизмов, который выполняет проверку
до того, как агент потратил хотя бы один токен.

### 2.3. MCP: ограничение, выраженное в интерфейсе (S1)

Спецификация Model Context Protocol фиксирует три вещи, прямо относящиеся к
теме контроля:

1. **Модель управляет инструментами, но не человеком.** Инструменты
   «model-controlled», однако «for trust & safety and security, there **SHOULD**
   always be a human in the loop with the ability to deny tool invocations»;
   приложениям предписано показывать, какие инструменты доступны, отмечать
   момент вызова и «present confirmation prompts to the user».
2. **Аннотации инструментов недоверенные.** «Clients **MUST** consider tool
   annotations to be untrusted unless they come from trusted servers». То есть
   даже машинно выраженное свойство действия не принимается на веру — прямая
   иллюстрация правила яруса: описание эффекта живёт на G3, а решение — на G5.
3. **Разделение ошибок протокола и ошибок исполнения.** Ошибки инструмента
   возвращаются в результате с `isError: true`, а не как отказ протокола. Это
   и есть условие информативности `E10` из
   [10-theory.md §3](10-theory.md): агент получает причину, а не «failed».

В разделе безопасности серверам предписано валидировать входы, ограничивать
частоту вызовов и санировать выходы, а клиентам — запрашивать подтверждение на
чувствительных операциях, показывать аргументы вызова пользователю **до**
отправки на сервер, валидировать результаты до передачи модели и вести журнал
вызовов для аудита. Последний пункт — ярус G7 в форме, не требующей изоляции.

## 3. Режимы отказа: таксономия MAST (S3)

Работа «Why Do Multi-Agent LLM Systems Fail?» (arXiv:2503.13657) строит
таксономию из **14 режимов отказа**, сгруппированных в три категории:
(i) проблемы проектирования системы, (ii) рассогласование между агентами,
(iii) отказ верификации задачи. Основание: 1600+ размеченных трасс по 7
популярным фреймворкам; таксономия выведена на 150 трассах при согласии
экспертов κ = 0.88.

Распределение: **спецификация и дизайн — 41.8%**, **рассогласование между
агентами — 36.9%**, **верификация — 21.3%**. Среди наиболее частых конкретных
режимов — неверная интерпретация задачи, «схлопывание» контекста, некорректная
верификация и завершение работы до фактического выполнения задачи.

**Почему это центральный кейс для темы #457.** 41.8% + 36.9% = **78.7%**
отказов относятся к тому, *как задача поставлена и как передана*, а не к тому,
насколько хорошо агент проверяет результат. Это независимое (не вендорское)
подтверждение того, что предметом инженерии является постановка, а не только
исполнитель. Ограничение доказательности: препринт, разметка человеческая,
распределение зависит от состава задач.

## 4. Наблюдаемость: OpenTelemetry GenAI semantic conventions (S1/S5)

Семантические конвенции OpenTelemetry для GenAI задают стандартную схему
телеметрии: дерево спанов с верхнеуровневым `invoke_agent` и дочерними `chat`
(вызовы модели) и `execute_tool` (вызовы инструментов), с атрибутами
`gen_ai.request.model`, `gen_ai.usage.input_tokens`,
`gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons`, а при включённой
записи содержимого — `gen_ai.system_instructions`, `gen_ai.input.messages`,
`gen_ai.output.messages`. Конвенции развиваются в рамках CNCF; поддержка
заявлена рядом платформ наблюдаемости, а фреймворки (в том числе LangChain,
CrewAI, AutoGen) эмитируют совместимые спаны нативно или через инструментацию.

**Что это меняет для рамки.** Ярус G7 в форме «аудит постфактум» перестал быть
вендорской привязкой: `E12 Trace` из [10-theory.md §2](10-theory.md) стал
переносимым артефактом. Что стандарт **не** покрывает — семантику решения:
в спанах есть выбранное действие, но нет отвергнутых альтернатив, а именно они
делают инициативу наблюдаемой (H14).

а не как вывод.

## 6. Тренды 2024–2026: миграция ограничений вниз по ярусам

Наблюдаемое направление развития рассмотренных источников — перенос
ограничений с яруса G1 (текст) на ярусы G3–G7 (контракт, рантайм, среда):

| Было | Стало | Пример |
| --- | --- | --- |
| «не вызывай опасные инструменты» в системном промпте | политика прерывания по имени инструмента и предикату на аргументах | `interrupt_on`, `when` (§2.1) |
| «проверь вход» в промпте | функция-гардрейл с исключением по `tripwire_triggered` | (§2.2) |
| «инструмент только читает» в описании | объявленное свойство эффекта + недоверие к объявлению на стороне клиента | аннотации MCP (§2.3) |
| «залогируй, что делал» | стандартная схема спанов `invoke_agent` / `execute_tool` | OTel GenAI (§4) |
| «перепроверь себя» | внешний банк критиков в цикле генерации | LLM-Modulo, [20 §2](20-taxonomy.md), P6 |

Обратного движения — переноса критических правил обратно в промпт — в
рассмотренных источниках не наблюдается. Это самое сильное из наблюдений
данного файла, и оно же — самое уязвимое: выборка из шести фреймворков не
является рынком.
