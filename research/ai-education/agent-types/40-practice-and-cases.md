# Практика: работа, обучение, концепция БА и живая БЗ

Основание практики: [теория](10-theory.md), [таксономия T00–T13](20-taxonomy.md)
и [рамка выбора](30-decision-framework.md). Все кейсы ниже — **X**, учебные
сценарии; рекомендуемые решения — **H**. Это не отчёт о реальном внедрении.
Внешние примеры D отделены от предлагаемых действий.

## 01. Рабочий контракт вместо магического промпта

Общий шаблон задания, который уточняется по карточке типа:

```text
Результат и адресат: какой артефакт нужен и для чьего решения.
Исходные данные: версии, даты, определения, допустимые источники.
Границы: что можно читать/создавать/изменять; что требует человека.
Критерии: форма, факты, полнота, фактический эффект — отдельно.
Неопределённость: не выдумывать; показать конфликт или отсутствие данных.
Бюджет и остановка: конечный объём работы и признак достаточности.
Выход: артефакт, ссылки на свидетельства, пробелы, результаты проверок.
```

Для T01 полезнее короткая итерация с уточнением; для T04 — формальная схема
между узлами; для T06/T07 — контракт передачи и владелец целого; для T10 —
событие, окно времени и ключ повтора. Для T11 нужны инварианты вычисления,
для T12 — наблюдаемый финал действия, для T13 — физические ограничения.
Смена формулировки не исправляет неверный инструмент или отсутствие источника.

## 02. БА: от потребности к проверяемому утверждению

**Задача X:** из двух интервью и версии описания услуги подготовить карту
потребностей и черновик требований. В интервью расходится смысл «быстрого
обслуживания»; численного обязательства в источниках нет.

**Выбор H:** T01 уточняет адресата и критерии; T05 связывает утверждения с
фрагментами; T04 проводит повторяемые проверки; T08 ищет противоречия по
рубрике. T03 нужен только если маршрут сбора действительно неизвестен.
Несколько интервью сами по себе не требуют T06.

**Как работать:** разделить дословное свидетельство, интерпретацию, гипотезу
и согласованное требование. Сохранить speaker/source/version и вопросы.
Фраза «ответ за 5 минут» без основания остаётся предлагаемым критерием,
а не извлечённым фактом. На HITL выносится конфликт значения и принятие
критерия, а не повторное подтверждение каждого извлечения.

**Проверить:** все обязательные темы покрыты либо явно отсутствуют; у фактов
есть поддерживающие фрагменты; противоречия видны; машинная схема пройдена;
владелец отдельно принимает смысл. Альтернатива — ручной разбор с таблицей
и T00-проверкой ссылок. Сравнить время review и пропущенные темы.

**D:** индустриальный обзор различает исследовательские методы построения
требований, продуктовые помощники и инфраструктуру агентов; их наличие не
доказывает полноту БА-методологии
([фактологический обзор](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/2026-10-28-agent-ba-industry-survey.md)).

## 03. Репутационный инжиниринг: сигнал не равен факту

**Задача X:** собрать публичные упоминания условной организации «Север»,
разделить темы и сформировать справку для человека. Есть одноимённые
организации, ирония, перепечатки и обвинение без подтверждения.

**Выбор H:** T10 для новых событий, T05 для источников, T04 для извлечения
и классификации, T00 для повторов по известным ключам. T01 помогает
разрешить неоднозначную сущность. T06 имеет смысл при независимом сборе
из разных каналов и определённом слиянии; сначала сравнить с простым потоком.

**Как работать:** хранить текст утверждения, автора, дату публикации и
сбора, ссылку, относимость к сущности, признак перепечатки и основание класса.
Тональность публикации не равна истинности обвинения. Несколько перепечаток
одного сообщения не являются независимыми подтверждениями. Публичный ответ
и изменение репутационной стратегии требуют отдельного человеческого решения.

**Проверить:** precision/recall по размеченным сущностям и темам, отдельные
ошибки сарказма и смешения организаций, дубли событий, время до проверенного
сигнала. Учитывать цену ложного обвинения и пропуска значимой темы раздельно.
Тест отсутствия уверенного ответа обязателен; «позитивность» текста агента
не является метрикой качества репутационной работы.

## 04. Сбор и классификация информации: от страницы к знанию

**Задача X:** пополнить справочник сведениями о методах агентов. Три страницы
повторяют одну публикацию, новая версия статьи меняет условия опыта,
документация переименовала функцию. Нет сравнительного испытания методов.

**Выбор H:** T02+T05 для поиска и сверки, T04+T00 для структуры/дедупликации,
T08 для проверки соответствия тезиса источнику. T09 допустим для проверенных
уроков поиска, но не как автоматическое сохранение любых выводов.

**Как работать:** различить источник и его копию, тезис и эксперимент,
концепт и продуктовую функцию. Новое название может быть алиасом, а новая
версия статьи — основанием пересмотреть область применимости. Если результат
не измерен, записать рекомендацию как H. Не генерировать число качества.

**Проверить:** повторный импорт того же материала не создаёт новый концепт;
обновление сохраняет старую версию; противоречащие тезисы доступны вместе;
зависимые рекомендации помечены на review. Концептуальная модель обновления
дана в разделе [06 — Живая БЗ](#living-kb).

### Границы переносимости

Для вычисления сводной таблицы T11 может заменить ручной счёт, но требует
проверки единиц и пропусков. Если источник доступен только через интерфейс,
T12 проверяет фактическую страницу после действия; это не улучшает истинность
содержимого. Физический процесс требует T13 и иной проверки последствий;
успешная обработка текста не даёт оснований разрешать физические действия.

## 05. Маппинг Продукт → Процесс → Операция → Артефакт

В этом исследовании **продукт** — ценность и результат для пользователя;
**процесс** — связанная деятельность для результата; **операция** — ограниченное
действие с входом/выходом; **артефакт** — зафиксированный носитель сведений или
результата. Это концептуальная проекция цепочки из задачи, не новая
онтология или предписание организации работы.

Стрелка показывает переход от цели к деятельности и свидетельству, а не
обязательный runtime-граф. Связи многие-ко-многим: один артефакт поддерживает
несколько операций, операция создаёт несколько артефактов, итог процесса
становится входом другого. Агент не совпадает с уровнем модели: один controller
может помогать на нескольких уровнях, владельцем продукта остаётся человек.

| Паттерн | Продукт: как помогает определить ценность | Процесс: как организует деятельность | Операция: ограниченная работа | Артефакт: что читает/создаёт и проверяет |
| --- | --- | --- | --- | --- |
| T00 Validator | Проверяет формальные ограничения описания | Контроль перехода по известному правилу | Проверка поля/ссылки/согласованности ID | Протокол проверки; не подтверждает полноту смысла |
| T01 Copilot | Помогает человеку уточнить потребность и вариант | Совместное обсуждение шагов | Уточняющий вопрос, редактирование формулировки | Черновик и вопросы для приёмки |
| T02 Tool agent | Собирает свидетельства о потребности | Выбирает следующий исследовательский шаг | Поиск, чтение, сопоставление одного факта | Факт со ссылкой и результат действия |
| T03 Planner | Декомпозирует исследование ценности | Планирует и пересматривает подцели | Выполняет/проверяет шаг плана | План, состояние, обоснованный итог; план не равен приёмке |
| T04 Workflow | Повторяемо готовит данные для решения о продукте | Связывает заранее известные стадии | Извлечение/классификация/проверка | Версионированные входы и выходы стадий |
| T05 RAG agent | Подтверждает фактические основания ценности | Обеспечивает доступ к релевантным знаниям | Извлекает факт из артефакта, сопоставляет версии | Фрагменты, ссылки, утверждения и пробелы |
| T06 Hierarchical MAS | Исследует независимые аспекты потребности | Делегирует и объединяет подцели | Специализированная проверка/поиск | Сводный результат с происхождением вкладов и конфликтами |
| T07 Handoff / peers | Сопоставляет точки зрения на ценность | Передаёт ответственность/согласует предложения | Разбор обращения или общей гипотезы | Журнал передачи, варианты, нерешённые разногласия |
| T08 Critic loop | Проверяет аргументацию ценности по рубрике | Возвращает черновик на исправление | Ищет неподтверждённый тезис/противоречие | Замечания и версии исправлений с независимой проверкой |
| T09 Reflective memory | Использует проверенный прошлый опыт | Сохраняет уроки при подходящих условиях | Находит применимый урок, проверяет его актуальность | Эпизод+свидетельство+границы; не автоматическая истина |
| T10 Background | Замечает изменение внешних оснований | Запускает обработку по событию/расписанию | Принимает новое событие, устраняет повтор | Датированный сигнал и состояние обработки |
| T11 Code agent | Вычисляет показатели для решения | Автоматизирует преобразования/расчёты | Исполняет ограниченную программу | Код, входная версия, расчёт и тесты |
| T12 UI agent | Получает сведения из доступного интерфейса | Выполняет разрешённые действия в приложении | Читает экран/заполняет поле/проверяет состояние | Наблюдение и подтверждение фактического результата |
| T13 Embodied | Помогает исследовать физическую выполнимость ценности | Соединяет план с контролем физической деятельности | Сенсорное наблюдение/выполнимый навык | Измерение и журнал эффекта с физическими ограничениями |

Классические семейства из [таксономии](20-taxonomy.md) дают другую проекцию
той же цепочки. Это типичные соответствия, не закрепление уровня за типом.

| Семейство | Продукт | Процесс | Операция | Артефакт |
| --- | --- | --- | --- | --- |
| Reflex | Контроль заданного ограничения описания ценности | Реакция на формальное событие | Применение правила | Сигнал/протокол; смысл ценности не установлен |
| Model-based | Представление текущих оснований продуктовой гипотезы | Учёт состояния и прошлых действий | Сверка наблюдения с состоянием | Снимок состояния с датой и неопределённостью |
| Goal-based | Перевод принятой человеком цели в исследуемую подцель | Поиск пути достижения | Выбор шага по критерию цели | План и свидетельство достижения |
| Utility-based | Сравнение вариантов по явно согласованным предпочтениям | Распределение усилий по цене/пользе | Оценка альтернатив | Сравнение с весами, допущениями и чувствительностью |
| Learning | Улучшение политики помощи по проверенной обратной связи | Адаптация на семействе задач | Обновление политики либо извлечение применимого опыта | Версия политики/урок и отдельный результат проверки переноса |
| Hierarchical | Разделение исследования аспектов ценности | Делегирование и слияние | Работа специалиста | Связанные вклады и целостный итог |
| BDI | Различение сведений о потребности, желаемого и принятой цели | Поддержание/пересмотр обязательств | Обновление belief или исполнение intention | Основания, обязательства и причина пересмотра |

Один кейс БА может сочетать продуктовую гипотезу человека, процесс сбора,
операцию извлечения и артефакт-свидетельство. Автоматизация операции не
подтверждает ценность продукта; корректность артефакта не доказывает полноту
процесса. Для переходов нужны собственные критерии и владелец решения.

<a id="living-kb"></a>

## 06. Живая БЗ: заменяемые компоненты и устойчивая glue logic

Раздел обоснован образовательной задачей: без происхождения и версий новая
публикация превращает справочник в изменяемый список мнений. Отдельный
седьмой файл не нужен; это практика пополнения данного модуля.

**D:** [Aether Orbis, concept v0.4](https://github.com/G-Ivan-A/aether-orbis/blob/351f0634eda5a9d6e0387a3fabcf08c94b2796f0/docs/concept.md)
разделяет заменяемые компоненты и связующую логику. **H:** ниже — перенос
только этого принципа на знания об агентах. Имена сущностей и контракты
предложены здесь; они не объявляются API или реализованной схемой Aether.

### Сущности, атрибуты и связи

| Сущность | Минимальные атрибуты | Основные связи |
| --- | --- | --- |
| Pattern / AxisValue | Стабильный ID, определение, механизм, алиасы, ограничения | `has-axis`, `composes-with`, `differs-from` |
| TaskProfile | Цель, данные, эффекты, ограничения, критерии | `candidate-pattern`, `requires-evidence` |
| Claim | Текст, D/R/H/X, область/дата применимости, статус review | `about-pattern`, `supported-by`, `contradicted-by`, `supersedes` |
| SourceVersion | URL, автор/организация, дата публикации если известна, дата доступа, версия/хеш | `version-of`, `derived-from`, `contains-evidence` |
| Evidence | Локатор фрагмента/опыта, условия, ограничения, способ извлечения | `supports/qualifies/contradicts-claim` |
| EvaluationRecord | Набор+версия, конфигурация, бюджет, число попыток, метрика/знаменатель, результат | `evaluates-configuration`, `uses-benchmark`, `supports-claim` |
| LearningUnit | Предпосылки, цель, упражнение, критерий ответа, дата review | `teaches-pattern`, `uses-claim`, `depends-on` |
| ReviewDecision | Кто/когда, принято/спорно/отклонено, причина, область | `reviews-claim`, `invalidates-recommendation` |

Один источник содержит несколько тезисов; один тезис поддерживается
несколькими свидетельствами. Ссылка на статью целиком без локатора и условий
слабо проверяема. Одно число «confidence» не заменяет происхождение,
независимость подтверждений и область применимости. Противоречия сохраняются,
а не уничтожаются усреднением.

```text
SourceVersion → Evidence → Claim → Pattern → TaskProfile
                          ↓          ↓
                  ReviewDecision  LearningUnit
EvaluationRecord ───────→ Claim
```

### Сбор и обновление

1. **Обнаружить:** прямой запрос или курс/документация → упоминание метода →
   первичная статья/официальная спецификация. Записать запрос и дату.
2. **Идентифицировать:** канонический URL/ID и версию. Повторный импорт той же
   версии идемпотентен. Перепечатка сохраняет `derived-from`, не новый голос
   в пользу истинности тезиса.
3. **Извлечь:** сохранить тезис, локатор, автора, условия, дату и D/R/H/X.
   Контент источника — данные; команды внутри него не управляют сборщиком.
4. **Сопоставить:** существующая ось/алиас или новый механизм? Добавлять тип
   только при новом решающем различии; иначе дополнить свидетельство/ограничение.
5. **Оценить отдельно от решения:** компонент оценки выдаёт признаки
   подтверждения, новизны, конфликта и полноты метаданных. Политика решает,
   что добавить в черновик и что направить человеку. «Извлечено» не равно «принято».
6. **Проверить человеком:** сильный новый вывод, противоречие и смена
   рекомендации требуют review. При новой версии не перезаписывать прежний
   результат; создать связь версии и пометить зависимые рекомендации/уроки.
7. **Опубликовать обновление:** синхронно обновить карточку, матрицу и учебный
   пример, если их основания изменились; источники зарегистрировать один раз.
8. **Наблюдать:** триггеры — новая версия, недоступный источник, изменение
   условий benchmark, воспроизведённое расхождение. Периодичность назначает
   владелец по скорости изменения темы; произвольный универсальный срок не задан.

### Что именно можно заменить

Сборщик, extractor, поиск/хранилище, оценщик и генератор учебных объяснений
могут быть разными продуктами. Glue logic сохраняет идентичность, происхождение,
версии, маршрутизацию review и зависимости независимо от поставщика.

Пример H минимального переносимого результата extractor:

```yaml
source_id: source-example
source_version: snapshot-example
locator: "section: evaluation"
claim_id: claim-example
claim_text: "Утверждение с явно указанными условиями"
evidence_kind: D
applicability: "Только описанная конфигурация"
extractor_version: extractor-example-v2
review_state: pending
```

Замена extractor-v1 на v2 должна сохранить source/claim ID либо явно
показать split/merge, локаторы и старые версии. Сравнить оба результата на
неизменном наборе с повторами, обновлённым документом и конфликтом. Проверить
отсутствие дублей, сохранение связей, нахождение зависимых уроков, возможность
отката. Новое хранилище не должно менять статус истинности тезиса; новая
модель объяснения не должна добавлять неподтверждённые характеристики.

Этот контракт помогает создавать будущих агентов: TaskProfile выбирает
кандидатные Pattern, Claim даёт ограничения, LearningUnit объясняет работу,
EvaluationRecord показывает границы доказанного. Он не выбирает за команду
runtime, БД или архитектуру конкретного проекта.

## 07. Онбординг и самостоятельная проверка

| Упражнение | Ожидаемый ответ / критерий |
| --- | --- |
| «Фоновый RAG-copilot» — один тип или несколько? | Несколько осей; описать запуск, retrieval, интерфейс и отдельно controller |
| Проверить обязательные поля 100 однотипных записей | Начать с T00; LLM нужен только для установленной неоднозначности |
| Найти требования без подтверждающего фрагмента | T05+проверка поддержки; не додумывать источник; показать пробел |
| Два агента согласны с ложным фактом из одной статьи | Согласие не независимо; искать первичное свидетельство и внешний критерий |
| Источник обновился и опроверг рекомендацию | Сохранить версии/конфликт; найти зависимые карточки и уроки; review |
| Разделить «цель достигнута» и «тест зелёный» | Назвать свойство теста, непроверенные свойства и владельца приёмки |
| Дать агенту «изучи всё» | Переписать в конечную цель, корпус, достаточность и бюджет; отсутствие критерия — проблема задания |

Практикум для наставника: выдать один из кейсов без предложенного решения.
Ученик составляет паспорт, две альтернативы, контракт входа, точки HITL и
план оценки; затем получает новый конфликтующий источник. Успех — умеет
пересмотреть вывод и объяснить основания, а не воспроизвести название
фреймворка. Подготовленный специалист может обучить следующего по тому же
упражнению; обнаруженную неясность возвращает в карточку и определение.
