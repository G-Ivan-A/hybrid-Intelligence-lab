# Метод, источники, открытые вопросы и пересмотр

<a id="method"></a>

## 01. Research Method и насыщение

**Вопрос:** как получить переносимую карту типов и научить выбору/работе,
не превратив её в рейтинг поставщиков? Метод — сравнительное чтение первичных
механизмов, классификаций компаний и учебных траекторий с проверкой границ.
Дата обращения ко всем веб-источникам — 2026-10-28.

| Поисковый проход | Воспроизводимые запросы / маршрут | Что изменилось в карте |
| --- | --- | --- |
| Прямые классификации | `site:anthropic.com building effective agents`; `site:cloud.google.com what are ai agents`; `site:aws.amazon.com what is ai agents` | Отделены фиксированное/динамическое управление, взаимодействие и классические политики |
| Косвенно через образование | `site:huggingface.co learn agents-course agent types`; `site:microsoft.github.io ai-agents-for-beginners design patterns` → lessons/actions → ReAct/RAG, smolagents/ADK | Разделены представление действия, механизм, интерфейс и учебная последовательность |
| Проверка механизмов | ReAct → Reflexion / Tree of Thoughts; `site:aaai.org BDI agents theory practice Rao Georgeff 1995` | Память отделена от обучения весов, поиск — от MAS, намерение — от цели |
| Проверка оценки | GAIA, τ-bench, AgentBench, SWE-bench, WebArena → первичные публикации/официальный harness | Benchmark сопоставлен с задачей и ограничениями, не с маркетинговым классом |
| Граничная и повторная проверка | SayCan; ADK workflow docs; повторный поиск Microsoft/Hugging Face по типам и actions | Добавлена физическая граница; повторные списки накладываются на существующие оси, JSON/code уточняют действие |

Отбор: первичная статья для механизма/опыта, официальная документация для
поведения реализации, курс — для терминологии и порядка обучения. Поисковые
сниппеты и вторичные пересказы не служат доказательством качества. Открытые
абстракты подтверждают только прямо описанный вклад/границу; скрытые детали
экспериментов из них не восстанавливались. Курс не доказывает эффективность
метода, а статья об одном методе — превосходство всего семейства.

**Критерий насыщения:** новый источник должен добавлять механизм, решающее
различие оси, ограничение или контрпример. На последней проверке общих списков
новые названия свелись к уже выделенным осям; первичные исследования уточнили
их границы. Поэтому завершён этот срез, без квоты источников и без заявления,
что все возможные агенты перечислены. Новый механизм возобновляет исследование.
Семь классических семейств и 14 карточек — результат группировки, не цель счёта.

**Domain Methodology:** паспорт задачи → описание controller/знаний/эффектов →
сравнение достаточных композиций → проверка → ограниченное применение.
Она содержится в [теории](10-theory.md), [таксономии](20-taxonomy.md) и
[рамке выбора](30-decision-framework.md); это не порядок проведения обзора.

### Проверенные альтернативы и содержательные исключения

| Гипотеза / кандидат | Результат проверки границы |
| --- | --- |
| Все типы образуют одну лестницу автономности | Не выдерживает совмещения retrieval, background и MAS; заменена независимыми осями |
| Любая автоматизация — LLM-агент | T00 показывает достаточную детерминированную альтернативу; термин используется с явной шириной определения |
| Любой RAG динамически выбирает действия | Первичный RAG этого не требует; static retrieval отделён от agentic retrieval |
| Reflexion — обучение весов | Механизм языковой памяти не меняет веса; обучение политик оставлено отдельной осью |
| Несколько ролей всегда надёжнее | Нет универсального подтверждения; MAST показывает организационные отказы; нужен baseline при равном бюджете |
| Бренд/framework/protocol — самостоятельный тип | Включаются как реализации/интерфейсы, если раскрывают механизм, а не новый класс сами по себе |
| Требуется второй RRP или новый стандарт | Те же оси и решения обслуживают три домена; маппинг/БЗ помещаются в практике; отдельный модуль дублировал бы основания |
| Только BA-решения релевантны карте | Отклонено: веб, код и физическое действие выявляют границы, невидимые в текстовом БА |

«Проверка» здесь означает логический контрпример или сопоставление с
первоисточником; это не новый эксперимент, опровергающий все применения.
Узкий прикладной корпус не использовался для определения типов.

## 03. Обратная связь и открытые вопросы

Если практика воспроизводимо противоречит рекомендации (независимое
свидетельство либо собственный контролируемый замер), это дефект рамки:
создать задачу на пересмотр [выбора](30-decision-framework.md), связать кейс
с ней и проверить зависимые карточки. Если затронут смысл объекта —
пересмотреть [теорию](10-theory.md) и весь граф зависимостей. Одна вендорская
история успеха создаёт вопрос, а не автоматически меняет правило.
Механизм следует [RFC RRP, P5](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/docs/rfc/2026-07-17-rfc-reference-research-pattern.md).

| Приоритет / вопрос | Что нужно измерить | Когда пересмотреть |
| --- | --- | --- |
| Высокий: стоимость координации в БА и поиске | T03 против T06 при равных данных/бюджете: покрытие, конфликты, время review | Устойчивый выигрыш/проигрыш на отложенных задачах |
| Высокий: эффективность точек HITL | Ошибки до/после review и время человека, пропущенные критические решения | Контроль не ловит существенные ошибки либо чрезмерно тормозит результат |
| Средний: переносимость «толерантности к промпту» | Контролируемые пропуски цели/данных/формата на нескольких моделях | Измеренная зависимость позволяет заменить качественные советы числами |
| Средний: память против загрязнения | T09 с/без памяти на новых задачах, устаревшие уроки | Наблюдается вред или полезный перенос |
| Средний: замена компонентов БЗ | Импорт/конфликты/ID/версии и зависимые уроки до/после замены | Потеря provenance или изменение смысла при технической миграции |

Это будущие эмпирические вопросы, не отложенные части текущего справочника.
Текущая задача требует метод выбора и оценки; она не требует объявить
победителя без собственного измерения. Внешний доступ к runtime или модели
не нужен для проверки структуры и содержания этого результата.

## 04. Глоссарий

| Термин | Значение здесь |
| --- | --- |
| API / tool | Программный интерфейс / доступная агенту операция с эффектами |
| Controller | Логика выбора шага, остановки и обновления состояния |
| Workflow | Заранее заданный граф исполнения, возможно с LLM-узлами |
| RAG / retrieval | Генерация с извлечёнными сведениями / поиск релевантного материала |
| HITL | Участие человека в конкретных точках решения и приёмки |
| MAS / handoff | Несколько взаимодействующих агентов / передача ответственности |
| Grounding / provenance | Связь утверждения со свидетельством / его происхождение и версии |
| Harness / benchmark | Среда исполнения и оценки / набор задач с процедурой оценки |
| Baseline / ablation | Простая сравниваемая альтернатива / отключение компонента для проверки его вклада |
| Abstention / drift | Отказ от неподтверждённого вывода / изменение условий или поведения |
| Idempotence | Повтор обработки одного входа не создаёт повторного эффекта |
| Glue logic | Устойчивые связи и решающие переходы между заменяемыми компонентами |
