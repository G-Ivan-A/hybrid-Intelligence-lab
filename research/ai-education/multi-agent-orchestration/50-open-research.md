# Multi-Agent Orchestration: интеграция в конвейер, образовательный срез и открытые вопросы

## 1. Встраивание в Source Intelligence Engine

Разбор ведётся по стадиям конвейера `источники → парсинг → извлечение → граф →
API`. Для каждой стадии определяющим является не «сложность» стадии, а
**независимость единиц работы** и **стоимость слияния**.

| Стадия | Единица работы | Независимость | Рекомендуемая форма | Обоснование |
| --- | --- | --- | --- | --- |
| обнаружение и загрузка источников | источник/URL | полная | воркер-пул, **не** мультиагентность | это параллелизм данных: агенты ничем не обмениваются ([`20-taxonomy.md`](20-taxonomy.md), §4) |
| парсинг и нормализация | документ | полная | детерминированный конвейер + N экземпляров | стадия почти не требует рассуждения; агент здесь — избыточная стоимость |
| извлечение сущностей и связей | документ/чанк | высокая внутри документа | параллельные экстракторы с **общей** схемой и промптом | подзадачи аддитивны, слияние — это уже следующая стадия |
| разрешение идентичности и запись в граф | сущность | **низкая**: решения взаимозависимы | **один writer-агент/сервис** | конкурирующие писатели дают false merge/false split; принцип единственного писателя ([`10-theory.md`](10-theory.md), §7) |
| верификация и провенанс | утверждение | высокая | отдельный верификатор, не автор извлечения | 21.30% MAST-отказов — task verification ([Cemri et al.](https://arxiv.org/abs/2503.13657)) |
| исследовательские запросы поверх графа/API | вопрос | высокая при breadth-first | orchestrator-worker — единственный кандидат на явную мультиагентность | это тот самый класс, где Anthropic измерила выигрыш ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)) |

**Сводный вывод для SIE.** Мультиагентность в её содержательном смысле —
разные роли, обменивающиеся состоянием, — оправдана в конвейере ровно в двух
местах: **breadth-first исследовательские запросы** поверх готового графа и
**независимая верификация** извлечённых утверждений. Основной объём конвейера —
это параллелизм данных, который решается инфраструктурой, а не архитектурой
агентов и не платит ×15 токенов. Стадия записи в граф — явный кандидат на
запрет параллельных писателей.

Это исследовательская рекомендация, а не архитектурное решение: решение
принимает человек в отдельном RFC/ADR.

### 1.1 Cost of orchestration vs cost of sequential execution

| Что сравнивается | Последовательное исполнение | Оркестрация |
| --- | --- | --- |
| токены | базовая линия | +дублирование контекста +обратный трафик (≈×15 к чату в оценке Anthropic) |
| wall-clock | сумма стадий | max по ветке + слияние; выигрыш ограничен последовательной долей |
| отказоустойчивость | одна точка отказа, простой ретрай | ретрай ветки дешевле полного, но требует чекпоинтов |
| воспроизводимость | высокая | зависит от порядка слияния и недетерминизма планировщика |
| диагностика | линейный лог | дерево трейсов, нужна корреляция по ID |

Для data-интенсивного конвейера ключевое наблюдение: **выигрыш по wall-clock
достигается инфраструктурным параллелизмом дешевле, чем агентным.** Агентная
оркестрация покупается тогда, когда нужно не «быстрее обработать», а «решить,
что обрабатывать».

### 1.2 Связь с соседними модулями

| Модуль | Интерфейс к оркестрации |
| --- | --- |
| Retrieval | у каждого подагента свой retrieval-скоуп; дублирование запросов — прямая статья перерасхода токенов |
| Memory | общая память — механизм координации и одновременно источник рассогласования, если у записей нет владельца и провенанса |
| Task Processing | декомпозиция и терминация — это планирование; ярус автономии выбирается по обратимости действия |
| Information Extraction | параллельные экстракторы допустимы, параллельные писатели графа — нет; слияние требует канонизации и провенанса |
| Evaluation | верификатор не должен быть автором результата; нужны метрики на агента и на выполнение целиком |
| Tool Use | параллельные вызовы инструментов — конкурентность внутри агента, а не мультиагентность |
| Observability | трейс с деревом родитель→потомок — предусловие мультиагентности; точка схождения — OTel GenAI conventions ([OTel GenAI SIG](https://github.com/open-telemetry/semantic-conventions-genai/issues/35)) |

## 2. Образовательный срез (общий для всех ролей)

Раздел описывает то, что должно быть понятно **любой** роли, работающей с
AI-агентами. Специализация для конкретных ролей (бизнес-аналитик, разработчик,
архитектор, продуктовый менеджер) — **downstream-задача**, не входящая в этот
модуль.

### 2.1 Восемь концепций

1. **Мультиагентность — покупка, а не улучшение.** У неё есть прайс-лист:
   токены, латентность слияния, вероятность рассогласования, сложность отладки.
2. **Число агентов — следствие, а не решение.** Решаются четыре вопроса:
   декомпозиция, топология, владение состоянием, условие терминации.
3. **Граница между агентами — это место, где теряется контекст.** Каждая новая
   граница добавляет вероятность рассогласования (36.94% отказов по MAST).
4. **Плохая постановка умножается на число агентов.** Крупнейшая категория
   отказов — specification issues (41.77%).
5. **У каждого объекта состояния — один писатель.** Читателей может быть много.
6. **Верификатор не может быть автором.** Самопроверка систематически не
   срабатывает; это отдельная роль (21.30% отказов).
7. **Согласие не равно корректности.** Голосование не устраняет коррелированный
   bias одной модели; панель полезна ортогональностью перспектив, а не числом.
8. **Без трейса мультиагентности не существует.** Нельзя управлять тем, что
   нельзя локализовать и посчитать.

### 2.2 Типичные ошибки и исправляющие вопросы

| Ошибка | Вопрос, который её снимает |
| --- | --- |
| «сделаем команду агентов» | Какая подзадача выполняется, не зная результата другой? |
| преждевременный параллелизм | Можете описать merge-функцию до запуска? |
| роли из оргструктуры | Какой объект состояния принадлежит этой роли? |
| нет единого источника истины | Кто единственный писатель этого объекта? |
| дебаты вместо верификации | Какой проверяемый критерий, кроме согласия панели? |
| нет условия остановки | Каким предикатом выражается «готово»? |
| «мультиагентность ускорит» | Какая доля работы действительно независима? |
| стоимость не измерена | Сколько токенов и времени на агента, включая p95? |
| «в статье это сработало» | На каком классе задач и с какой связанностью подзадач? |
| смена архитектуры без baseline | Что показывает один агент на том же наборе? |

### 2.3 Trade-offs, которые обязана понимать любая роль

| Ось | Что выигрываем | Чем платим |
| --- | --- | --- |
| надёжность | изоляция контекста, независимая верификация | новые режимы отказа на границах агентов |
| стоимость | распараллеленное покрытие | ≈×15 токенов относительно чата |
| скорость | до −90% wall-clock на независимых ветках | последовательная доля не ускоряется; слияние добавляет латентность |
| отладка | локализация по ролям при хорошем трейсе | без трейса — комбинаторный рост пространства диагностики |
| гибкость | динамические маршруты | непредсказуемая стоимость и недоказуемая терминация |

### 2.4 Проверяемые формулировки требований

Непроверяемое: «система использует мультиагентную архитектуру для повышения
качества».

Проверяемое: «(a) названы подзадачи и доказана их независимость; (b) описана
merge-функция; (c) у каждого объекта состояния назван единственный писатель;
(d) верификация выполняется агентом, не являющимся автором результата;
(e) выполнение трассируется с деревом родитель→потомок; (f) зафиксированы
токены и p95-латентность на выполнение; (g) есть baseline одного агента на том
же наборе задач».

## 3. Открытые вопросы для локальной проверки

- Какая реальная доля независимой работы в наших исследовательских запросах —
  то есть где мы находимся на матрице §3 [`30-decision-framework.md`](30-decision-framework.md)?
- Воспроизводится ли соотношение ×4/×15 на наших моделях, задачах и длине
  контекста, или это профиль конкретного вендора и класса задач?
- Каково распределение MAST-категорий на наших собственных трейсах — совпадает
  ли оно с 41.77/36.94/21.30?
- Даёт ли наша панель из трёх ортогональных перспектив измеримо больше
  уникальных возражений, чем три прогона одного исполнителя при равном бюджете?
- Какова цена false merge против false split при параллельной записи в граф и
  оправдывает ли она единственного writer-агента количественно?
- Какой минимальный набор атрибутов трейса достаточен для локализации отказа до
  конкретного агента?
- Где проходит наша граница окупаемости: при какой ценности результата ×15
  токенов перестаёт быть приемлемым?
- Какая стоимость миграции между фреймворками, если логика декомпозиции вынесена
  из SDK, — и подтверждается ли гипотеза «паттерн переживает SDK»?

## 4. Минимальный следующий эксперимент

Взять 20–30 реальных исследовательских запросов к будущему графу. Прогнать три
конфигурации на одном наборе: (1) один агент с retrieval; (2) параллельная
секция с механическим слиянием; (3) orchestrator-worker. Измерить: успешность по
заранее заданному критерию, покрытие источников, токены и p95-латентность,
долю выполнений с рассогласованием, время локализации отказа. Результат — не
«лучшая архитектура вообще», а положение нашей задачи на матрице выбора и
локальная точка окупаемости. Эксперимент требует предварительно работающего
трейсинга — без него измерять нечего.

## 6. Ограничения обзора

Локальный бенчмарк не выполнялся: все количественные значения взяты из внешних
источников и переносятся на наш контекст только как порядок величины. Ключевые
цифры Anthropic (×4/×15 и +90.2%) получены на закрытом внутреннем eval, протокол
не опубликован и независимо не воспроизведён. Доли MAST измерены на семи
сторонних фреймворках 2024–2025 и могут не совпадать с профилем нашего стека.
Статусы фреймворков и протоколов проверены на 2026-08-11 и в этой области
меняются быстро — консолидация AutoGen и Swarm за один год тому подтверждение.
Обзор не оценивал безопасность мультиагентных систем, стоимость владения
инфраструктурой и лицензионные ограничения фреймворков.
