# Multi-Agent Orchestration: фреймворки, протоколы и практика

## 1. Ландшафт на дату исследования (2026-08-11)

Первое, что должен зафиксировать обзор 2026 года, — **консолидация**. Два из
шести фреймворков, названных в постановке задачи, изменили статус:

| Фреймворк из постановки | Статус на дату проверки | Что вместо него |
| --- | --- | --- |
| OpenAI Swarm | образовательный/экспериментальный, README рекомендует миграцию для production | [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) (март 2025) |
| AutoGen | режим сопровождения: багфиксы и патчи безопасности, без новых паттернов оркестрации | [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/overview/) 1.0 (апрель 2026), объединивший AutoGen и Semantic Kernel |

Это само по себе — вывод для архитектуры: **срок жизни SDK короче срока жизни
паттерна**. Sequential, orchestrator-worker и evaluator-optimizer пережили смену
двух поколений фреймворков; конкретные API — нет.

## 2. Сравнение

| Фреймворк | Модель исполнения | Механизм состояния | Поддерживаемые паттерны | Отладка / observability | Границы применимости |
| --- | --- | --- | --- | --- | --- |
| [LangGraph](https://langchain-ai.github.io/langgraph/) | явный граф узлов и рёбер | типизированная схема состояния + редьюсеры для слияния конкурирующих обновлений; чекпоинтер даёт durable execution и возобновление после сбоя | sequential, routing, parallel, supervisor, swarm-handoff, циклы с условием | трейсинг узлов, снимки состояния, интеграция с LangSmith | требует явного проектирования схемы состояния; это преимущество, но и порог входа |
| [CrewAI](https://docs.crewai.com/en/introduction) | Flows как каркас процесса + Crews как автономные команды внутри шагов | состояние Flow сохраняется между шагами и запусками | sequential, hierarchical, event-driven Flow | встроенная телеметрия, OTel-инструментирование | автономия Crew ограничена явным Flow — документация рекомендует «начинать с Flow» |
| [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/overview/) | агенты + workflows с явным контролем путей исполнения | session-based state management, типобезопасность, фильтры, телеметрия | single/multi-agent паттерны AutoGen + workflows, human-in-the-loop | телеметрия из наследия Semantic Kernel | молодой объединённый API (1.0 с апреля 2026); миграционная стоимость с AutoGen |
| [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) | агенты с handoff и guardrails | контекст выполнения + встроенный tracing | routing/handoff, orchestrator-worker | встроенный трейсинг «из коробки» | наследует лёгковесную модель Swarm; ориентирован на стек OpenAI |
| [MetaGPT](https://github.com/FoundationAgents/MetaGPT) | ролевой конвейер, кодирующий SOP разработки ПО | артефакты между ролями (требования → дизайн → код) | sequential/hierarchical по SOP | зависит от инструментирования | SOP заточен под software engineering, что затрудняет перенос в другие домены ([OWL, NeurIPS 2025](https://proceedings.neurips.cc/paper_files/paper/2025/file/48dcc43a534c5b582f9d0fdb778e9b84-Paper-Conference.pdf)) |
| [CAMEL-AI](https://www.camel-ai.org/) / [OWL](https://github.com/camel-ai/owl) | role-playing диалог агентов; OWL добавляет Workforce с разделением планирования и исполнения | общий контекст диалога, обмен через сообщения | role-playing, workforce/hierarchical | зависит от инструментирования | исследовательский центр тяжести; OWL — лидер среди open-source на GAIA (58.18) |

Таблица фиксирует **документированные возможности**, а не сравнительный
бенчмарк. Ни один из фреймворков не решает за архитектора три ключевых вопроса:
как декомпозировать задачу, кто владеет каждым объектом состояния и по какому
предикату система останавливается.

## 3. Критерии выбора

| Потребность | Первый shortlist | Почему |
| --- | --- | --- |
| детерминированный конвейер с восстановлением после сбоя | LangGraph | чекпоинты и явная схема состояния |
| .NET/enterprise-стек, human-in-the-loop, комплаенс | Microsoft Agent Framework | наследие Semantic Kernel: фильтры, типобезопасность, телеметрия |
| быстрый прототип ролевой команды | CrewAI | самый низкий порог входа для «команды с ролями» |
| стек OpenAI, минимум абстракций | OpenAI Agents SDK | handoff и tracing без графовой машинерии |
| исследование ролевого взаимодействия | CAMEL / OWL | центр тяжести на самих протоколах взаимодействия |
| взаимодействие агентов через организационные границы | A2A поверх любого из фреймворков | это протокольный, а не фреймворковый уровень |

Выбор проверяется spike на одной реальной подзадаче со снятыми метриками:
токены на агента, wall-clock, доля успешных выполнений, воспроизводимость трейса
и стоимость миграции. Vendor lock-in оценивается по возможности выгрузить
трейсы в OTel-совместимом виде и по тому, насколько логика декомпозиции
отделима от SDK.

### 3.1 Применимость к графовым результатам

Ни один из перечисленных фреймворков не предоставляет из коробки
ontology-aware слияние графовых фрагментов от параллельных агентов: канонизацию
идентификаторов, разрешение false merge / false split и провенанс. Всё, что дают
фреймворки, — детерминированный редьюсер состояния (LangGraph) или общий store.
Семантика слияния остаётся доменным кодом. Это прямо смыкается с выводами
модуля Information Extraction & Graph Modeling: параллельные экстракторы
безопасны, **параллельные писатели графа — нет**.

## 4. Разбор кейсов

| Кейс | Архитектура | Результат | Что из него следует |
| --- | --- | --- | --- |
| [Anthropic Research](https://www.anthropic.com/engineering/multi-agent-research-system) | orchestrator-worker: ведущий Opus 4 + подагенты Sonnet 4, параллельный поиск | +90.2% к одиночному Opus 4 на внутреннем research-eval; до −90% wall-clock; ≈×15 токенов | breadth-first поиск — канонический класс, где команда окупается; вендор сам перечисляет контрпоказания |
| [Cognition / Devin](https://cognition.com/blog/dont-build-multi-agents) | отказ от подагентов в пользу однопоточного агента с компрессией контекста | подагенты делали несовместимые допущения, интеграция не спасала | инженерия единого артефакта — канонический класс, где команда проигрывает |
| [MAST](https://arxiv.org/abs/2503.13657) | мета-анализ 1 000+ трейсов из 7 фреймворков | 14 режимов отказа: 41.77% / 36.94% / 21.30% | отказы носят организационный характер и повторяются между фреймворками |
| [MAD-сравнение](https://arxiv.org/abs/2311.17371) | контролируемое сравнение debate-протоколов с не-debate стратегиями | нет устойчивого превосходства при равном бюджете; высокая чувствительность к настройке | дебаты нельзя закладывать как гарантированный прирост качества |
| [OWL / Workforce](https://proceedings.neurips.cc/paper_files/paper/2025/file/48dcc43a534c5b582f9d0fdb778e9b84-Paper-Conference.pdf) | разделение планирования и исполнения вместо жёсткого SOP | #1 среди open-source на GAIA (58.18) | доменно-независимая координация переносится лучше, чем зашитый отраслевой SOP |

Сопоставление первых двух строк — главный практический результат обзора: **два
компетентных инженерных коллектива пришли к противоположным архитектурам,
потому что решали задачи из разных клеток матрицы** ([`30-decision-framework.md`](30-decision-framework.md), §3).
Цитировать любой из этих кейсов как универсальный аргумент — методологическая
ошибка.

## 5. Практические anti-patterns

| Анти-паттерн | Механика отказа | Ранняя диагностика |
| --- | --- | --- |
| преждевременный параллелизм | подзадачи объявлены независимыми без проверки; зависимость вскрывается на слиянии | попросить описать merge-функцию **до** запуска: если её нельзя описать, подзадачи связаны |
| «агент на каждую роль оргструктуры» | роли копируются из штатного расписания, а не из структуры задачи | у роли нет собственного объекта состояния и собственного выхода |
| отсутствие единого источника истины | два агента правят одну сущность | не назван владелец объекта |
| подагент без спецификации | «изучи вопрос и вернись» → домысливание задачи (MAST specification issues) | инструкция подагента не содержит формата выхода и границ |
| дебаты вместо верификации | панель согласилась — считаем корректным | нет независимого проверяемого критерия, только консенсус |
| цикл без предиката терминации | агенты перекидывают управление, бюджет сгорает | нет условия выхода, выраженного проверяемым предикатом |
| оркестратор как единая точка отказа | ведущий агент теряет контекст — падает вся система | нет чекпоинта состояния до синтеза |
| измерение стоимости по одному прогону | ×15 проявляется на хвостах и повторах | нет p95 по токенам и латентности |
| мультиагентность вместо воркер-пула | N одинаковых агентов на N документов | агенты не обмениваются ничем — значит, это параллелизм данных |
| смена топологии и модели одновременно | нельзя отличить эффект архитектуры от эффекта модели | нет baseline с одним агентом на том же наборе |

## 6. Форма референсной реализации

```text
контракт задачи (immutable для исполнителей)
  -> декомпозиция с явной merge-функцией
  -> N исполнителей, каждый со своим объектом состояния и форматом выхода
  -> детерминированный редьюсер / канонизация
  -> независимый верификатор (не автор результата)
  -> эскалация конфликтов и необратимых решений человеку
  -> трейс: дерево агентов, токены, латентность, версии моделей и промптов
```

Порядок элементов существенен: контракт задачи и merge-функция определяются
**до** выбора числа агентов, а верификатор существует отдельно от исполнителей.
Оба требования выводятся напрямую из распределения MAST-отказов.
