# Golden Set `GS-DEV-01`: `hardware`, профиль устройства

> Актуально для синтеза 2026-09-08. Упоминание `kb/processed` ниже относится к
> проверенному тогда корпусу; KB перемещена в
> [`mango-ba-ai-runtime/docs/kb`](https://github.com/G-Ivan-A/mango-ba-ai-runtime/tree/main/docs/kb).

> **Синтетический эталон повышенного риска.** Документ никому не поставлялся,
> данные вымышлены. В отличие от `GS-CC-01` и `GS-API-01`, у этого эталона нет
> опоры даже на лексику корпуса: в доступных `runs/` и `kb/processed` нет ни
> одного документа домена `hardware`. Основание синтеза — правила профиля
> `P-DEVICE` и общая индустриальная практика описания абонентских устройств
> связи. Числовые значения §10 — заведомо условные и подлежат замене владельцем
> продукта; они присутствуют, чтобы показать **форму** требования, а не его
> величину.

**Продуктовый класс:** `hardware` → capability «Подключение абонентского
оборудования» → feature «Автонастройка устройства» → atomic function «Получение
конфигурации при первом включении».
**Профиль:** `P-DEVICE` — предмет документа физическое устройство. Слот `S-UI`
пуст по профилю, `S-INTEGRATION` обязателен, `S-NFR` расширен условиями
эксплуатации.
**Формат:** `F-CLASSIC`.
**Назначение эталона:** показать, что профиль с максимально далёким предметом —
физический объект вместо экрана — не требует ни одного слота вне словаря.

## 1. Термины и определения

| Термин | Определение | Источник |
| --- | --- | --- |
| Автонастройка | Получение устройством конфигурации с сервера без ручного ввода. | новое понятие настоящего документа |
| Сервер конфигураций | Служба платформы, выдающая конфигурацию по идентификатору устройства. | новое понятие настоящего документа |
| Первое включение | Включение устройства с заводскими значениями. | новое понятие настоящего документа |

## 2. Проблема, цель, границы изменения

**Проблема.** Абонентское устройство настраивается вручную на площадке клиента:
подключение занимает выезд инженера, ошибки ввода дают часть обращений в
поддержку.

**Цель.** Устройство при первом включении получает рабочую конфигурацию
самостоятельно.

**Границы.** В объёме — первичное получение конфигурации и её обновление по
расписанию. Вне объёма — прошивка устройства, физический монтаж, поставка и
складской учёт.

## 3. Текущее состояние и требуемая дельта

| # | Текущее состояние | Источник факта | Требуемая дельта |
| --- | --- | --- | --- |
| 3.1 | Конфигурация вводится инженером через веб-интерфейс устройства. | практика подключения | Устройство запрашивает конфигурацию само. |
| 3.2 | Соответствие устройства и клиента нигде не хранится. | отсутствует | Вести реестр «идентификатор устройства → аккаунт». |
| 3.3 | Поведение при недоступности сервера не определено. | отсутствует | Задать поведение и период повторов. |

## 4. Функциональные требования (системная логика)

| ID | Требование | Дельта из §3 |
| --- | --- | --- |
| ФТ-4.1 | Устройство при первом включении запрашивает конфигурацию по адресу, полученному от службы сети. | 3.1 |
| ФТ-4.2 | Сервер выдаёт конфигурацию только устройству, присутствующему в реестре и привязанному к активному аккаунту. | 3.2 |
| ФТ-4.3 | Устройство применяет полученную конфигурацию и подтверждает применение серверу. | 3.1 |
| ФТ-4.4 | При недоступности сервера устройство сохраняет предыдущую рабочую конфигурацию и повторяет запрос по расписанию §12. | 3.3 |
| ФТ-4.5 | Устройство, отсутствующее в реестре, получает отказ и не применяет конфигурацию. | 3.2 |

## 5. Описание решения

Устройство получает адрес сервера конфигураций от службы сети и обращается к
нему по идентификатору. Сервер сверяет идентификатор с реестром и выдаёт
конфигурацию, привязанную к аккаунту.

## 6. Настройки

| ID | Настройка | Значение по умолчанию | Кто изменяет |
| --- | --- | --- | --- |
| Н-6.1 | Период проверки обновления конфигурации | 24 ч | владелец продукта, не клиент |

Клиентских настроек нет: значение принадлежит продукту. Это слот, где `P-DEVICE`
отличается от `P-API` — он не пуст, но и не управляется пользователем.

## 7. UI-логика

**Нет по продукту (`P-DEVICE`).** У устройства нет экранов платформы.
Индикация состояния — аппаратная и описывается эксплуатационной документацией
устройства, а не документом требований к платформе.

## 8. Сценарии использования

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| СЦ-8.1 | Первое включение устройства из реестра. | Конфигурация получена и применена, состояние в реестре — `активно`. |
| СЦ-8.2 | Включение устройства, отсутствующего в реестре. | Отказ, конфигурация не применена, событие отказа зафиксировано. |
| СЦ-8.3 | Сервер недоступен при плановой проверке. | Устройство работает на прежней конфигурации, повтор по расписанию. |
| СЦ-8.4 | Аккаунт устройства заблокирован. | Конфигурация не выдаётся, состояние в реестре — `заблокировано`. |
| СЦ-8.5 | Питание пропало во время применения конфигурации. | После восстановления питания устройство работает на прежней конфигурации и повторяет запрос. |

## 9. Критерии приёмки

| ID | Требование | Критерий | Способ проверки |
| --- | --- | --- | --- |

| КП-9.5 | ФТ-4.4 | Прерывание питания в момент применения не приводит к неработоспособной конфигурации в 20 из 20 прогонов. | приёмка на стенде |

## 10. Нефункциональные требования

| ID | Требование | Значение |
| --- | --- | --- |
| НФТ-10.1 | Время выхода на связь от подачи питания | ≤ 90 с |
| НФТ-10.2 | Диапазон рабочих температур | 0…+40 °C |
| НФТ-10.3 | Питание | внешнее и питание по сетевому кабелю |
| НФТ-10.4 | Соответствие требованиям к оборудованию связи | подтверждается до поставки |
| НФТ-10.5 | Сохранность конфигурации при пропадании питания | конфигурация не теряется |

Строки `НФТ-10.2`…`НФТ-10.4` — то самое расширение слота, которого нет ни в
одном другом профиле: у профиля `P-DEVICE` есть физические условия
эксплуатации. Расширение остаётся **внутри** слота `S-NFR` и не создаёт нового.
