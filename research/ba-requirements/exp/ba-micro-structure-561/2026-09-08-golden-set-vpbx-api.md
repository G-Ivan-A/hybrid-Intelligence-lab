# Golden Set `GS-API-01`: `voice-ucaas`, интеграционный профиль

> Актуально для сверки лексики 2026-09-08. Упоминание `kb/processed` ниже
> сохраняет источник замера; KB перемещена в
> [`mango-ba-ai-runtime/docs/kb`](https://github.com/G-Ivan-A/mango-ba-ai-runtime/tree/main/docs/kb).

> **Синтетический эталон.** Документ никому не поставлялся, данные вымышлены.
> Основание синтеза — правило `GS-4`: в `runs/` нет ни одного документа
> продуктового класса с профилем `P-API`, поэтому эталон смоделирован из правил
> профиля (§6 [`20-taxonomy.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/artifact-micro-structure/20-taxonomy.md))
> и индустриальной практики описания программных интерфейсов. Лексика разделов
> сверена с корпусом `kb/processed/vpbx-api` (замер
> [`2026-09-08-kb-slot-fit-facts.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/2026-09-08-kb-slot-fit-facts.md)).

**Продуктовый класс:** `voice-ucaas` → capability «Программное управление
телефонией» → feature «События вызова» → atomic function «Уведомление о
завершении вызова».
**Профиль:** `P-API` — потребитель системы является программой. Слоты `S-UI` и
`S-SETTINGS` пусты **по профилю**, слот `S-INTEGRATION` обязателен и несёт
основную нагрузку документа.
**Формат:** `F-CLASSIC`.
**Назначение эталона:** показать, что смещение содержания в `S-INTEGRATION` не
меняет состав скелета — исчезает заполненность двух слотов, но не сами слоты.

## 1. Термины и определения

| Термин | Определение | Источник |
| --- | --- | --- |
| Уведомление | HTTP-запрос от платформы к URL клиента о наступлении события. | KB: `vpbx-api/notifications` |
| Подпись запроса | Значение, подтверждающее авторство уведомления. | KB: `vpbx-api/auth` |
| Доставлено | Клиент ответил кодом `200` в пределах таймаута. | новое понятие настоящего документа |

## 2. Проблема, цель, границы изменения

**Проблема.** Интегратор узнаёт о завершении вызова только опросом истории:
задержка до минуты, нагрузка на платформу растёт линейно от числа интеграций.

**Цель.** Доставлять факт завершения вызова в момент завершения.

**Границы.** В объёме — уведомление о завершении вызова и его повторная
доставка. Вне объёма — события начала и перевода вызова, запись разговора,
изменение существующих методов истории.

## 3. Текущее состояние и требуемая дельта

| # | Текущее состояние | Источник факта | Требуемая дельта |
| --- | --- | --- | --- |
| 3.1 | Факт завершения доступен методом истории вызовов по запросу. | KB: `vpbx-api`, раздел истории | Добавить исходящее уведомление в момент события. |
| 3.2 | Подпись запроса определена для входящих методов. | KB: `vpbx-api/auth` | Распространить ту же схему подписи на исходящие уведомления. |
| 3.3 | Поведение при недоступности клиента не определено. | отсутствует в KB | Задать политику повторов и отказа. |

## 4. Функциональные требования (системная логика)

| ID | Требование | Дельта из §3 |
| --- | --- | --- |
| ФТ-4.1 | Система формирует уведомление о завершении вызова не позднее 2 с после освобождения канала. | 3.1 |
| ФТ-4.2 | Система подписывает уведомление действующим ключом интеграции. | 3.2 |
| ФТ-4.3 | Система повторяет недоставленное уведомление по политике §12 и прекращает попытки после исчерпания. | 3.3 |
| ФТ-4.4 | Система фиксирует итог доставки каждого уведомления в журнале интеграции. | 3.3 |

## 5. Описание решения

Исходящее уведомление на зарегистрированный URL интеграции. Существующие
методы истории сохраняются без изменений: уведомление их дополняет, не
заменяет.

## 6. Настройки

**Нет по продукту (`P-API`).** URL и ключ интеграции задаются при регистрации
интеграции и настройкой продукта не являются: их изменение — не выбор
пользователя, а смена стороны интеграции.

## 7. UI-логика

**Нет по продукту (`P-API`).** Потребитель — программа. Экраны наблюдения за
интеграцией относятся к продуктовому классу `self-service-lk` и, если
понадобятся, описываются отдельной задачей.

## 8. Сценарии использования

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| СЦ-8.1 | Вызов завершён, клиент доступен. | Уведомление доставлено с первой попытки, в журнале — `доставлено`. |
| СЦ-8.2 | Клиент отвечает `500` на первые две попытки. | Третья попытка успешна, в журнале — `доставлено`, число попыток `3`. |
| СЦ-8.3 | Клиент недоступен всё окно повторов. | Попытки прекращены, в журнале — `не доставлено`, данные доступны методом истории. |
| СЦ-8.4 | Ключ интеграции отозван между событием и отправкой. | Уведомление не отправлено, в журнале — `отклонено: ключ недействителен`. |
