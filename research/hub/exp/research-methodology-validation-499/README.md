# exp: research-methodology-validation-499

Evidence container for the analysis report
[`../../../../docs/analysis/2026-08-11-research-methodology-validation.md`](../../../../docs/analysis/2026-08-11-research-methodology-validation.md),
issue [#499](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/issues/499).

## Что здесь проверяется

Гипотеза issue #499: на текущей итерации Хабу достаточно двух методологий
исследований — одиночного датированного отчёта и модуля `00…50` (Reference
Research Pattern). Проверить её нельзя, пока не измерен корпус: сколько
исследований какой формы существует, соблюдается ли форма, чем формы фактически
различаются.

Контейнер отвечает только на **формальную** часть вопроса. Он не оценивает
содержание исследований и не выбирает методологию — это делает родительский
Analysis.

## Метод

`scan-research.py` обходит `research/` и различает две формы по структуре дерева,
а не по названию:

- **module** — каталог, объявляющий себя модулем наличием точки входа `00-*.md`;
  фиксируются состав префиксов, совпадение с каноническими `00 10 20 30 40 50`,
  посторонние файлы внутри каталога, объёмы, статусы, `method`, ссылки на issue;
- **single** — одиночный файл `YYYY-MM-DD-name.md` вне модулей и вне `exp/`;
  фиксируются `type`, `status`, `scope`, `source`, объём, ссылки на issue.

Даты создания берутся из git history (`git log --diff-filter=A --follow`), а не
из frontmatter: `updated` переписывается при правках и датой появления артефакта
не является. Отдельно перечисляются контейнеры `exp/` с числом скриптов, данных
и логов — это признак, по которому формы различаются сильнее всего.

Классификатор намеренно не содержит содержательных правил: если бы он относил
артефакт к форме по смыслу, вывод анализа был бы предрешён разметкой.

### `scan-spokes.py` — расширение охвата на spoke-репозитории

Комментарий к PR #502 требует распространить инвентаризацию на research-практики
`mango_ba_prompts` и `clarify-engine-ai`. Эти репозитории не подмодули Хаба,
поэтому снимок снимается через GitHub API (`gh api`), а не с файловой системы.

Классификация такая же формальная — только путь, имя файла и frontmatter:
`hub-single` (`YYYY-MM-DD-name.md` — форма Хаба), `spoke-single`
(`YYYY-MM-DD_slug_vN.md` — наблюдаемая в спицах запись), `module-file`
(`00-*.md` … `50-*.md`) и `undated`. Отдельно перечисляется исполняемая
evidence base спицы: код и тесты под `research/`.

### Ограничения измерения

- Число строк — прокси объёма, а не содержательности; тренд по нему доказателен,
  порог «достаточного наполнения» — нет.
- Frontmatter разбирается плоско: только скалярные поля верхнего уровня, списки
  (`related_artifacts`) не читаются.
- Скрипт исключает собственный каталог (`SELF_PREFIX`), иначе инвентаризация
  учитывала бы себя и числа менялись бы от прогона к прогону.
- Атрибуция исполнителя (модель) и стоимость прогонов в репозитории и в метаданных
  PR отсутствуют, поэтому в инвентарь не попадают — см. пробел данных в отчёте.

Основной результат: **ни один из 23 документов не написан ни в одной из двух

(19 из 19 датированных файлов), а исполняемое доказательство хранит не в `exp/`,
а как покрытый тестами код (`scripts/research/retrieval_experiments.py`,
`tests/research/test_retrieval_experiments.py`).

#### Ограничения замера спиц

- Учитываются только `.md` в каталогах с research/analysis-нагрузкой; работа в
  issue, PR и вне этих каталогов не входит — числа являются нижней границей.
- Снимок снят с ветки по умолчанию; SHA зафиксирован в JSON, при повторном
  прогоне позже числа изменятся вместе с репозиториями.
- Требуется сеть и аутентифицированный `gh`.

## Воспроизведение

```bash
python3 research/hub/exp/research-methodology-validation-499/scan-research.py \
  --out research/hub/exp/research-methodology-validation-499/research-inventory.json
```

```bash
python3 research/hub/exp/research-methodology-validation-499/scan-spokes.py \
  --out research/hub/exp/research-methodology-validation-499/spoke-inventory.json
```

Первый скрипт сети не требует, работает по локальному дереву и git history;
второй обращается к GitHub API и требует аутентифицированного `gh`. Числа отчёта
воспроизводятся на коммите `f0a5326`; на более поздних коммитах они изменятся
вместе с корпусом — это ожидаемо, снимок датирован `repo_sha` внутри JSON.
