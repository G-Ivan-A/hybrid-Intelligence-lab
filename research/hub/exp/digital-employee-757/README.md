# Проверки и источники исследования методологии цифровых сотрудников

Родительский отчёт: [исследование #757](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/issue-757-d0d9f56d9fc3/research/hub/2026-11-28-digital-employee-methodology-survey.md).
Локальная ссылка на [тот же отчёт](../../2026-11-28-digital-employee-methodology-survey.md)
проверяется валидатором структуры evidence.
Замер сделан 2026-11-28. Этот каталог хранит доказательства исследования. Он не
является runtime цифрового сотрудника, LLM-судьёй или benchmark моделей.

## Гипотезы и метод

`measure.py` проверяет две вещи.

**1. Точная модель гейта (§5.2 отчёта).** Модель считает вероятность того,
что дефект пройдёт гейт из трёх LLM-судей. Сравниваются три правила:
один судья, большинство и «единогласно, иначе — человеку». Каждое
правило считается для двух профилей судей и четырёх значений общей
корреляции ошибок ρ.
- Профили судей: «оптимистичный» пропускает 1/5 дефектов, «соглашательский» —
  3/4.
- Значения ρ: 0, 3/10, 3/5 и 9/10.
- Корреляция задана смесью: с вероятностью ρ вся панель выносит один общий
  вердикт, иначе судьи голосуют независимо.
- Вероятности считаются дробями `fractions.Fraction`, без случайности.
- Разбор эскалаций человеком считается безошибочным. Поэтому выигрыш гейта —
  это верхняя граница.

Десять probes проверяют ключевые выводы с архитектурной, операционной,
security- и governance-перспектив:
- G-1: при независимых судьях единогласие снижает пропуск с 1/5 до 1/125.
- G-2: при полной корреляции панель не сильнее одного судьи.
- G-3: при ρ = 9/10 пропуск равен 113/625 ≈ 0,18.
- G-4: соглашательские судьи даже единогласно пропускают 27/64 дефектов.
- G-5: правило с эскалацией снижает ложный пропуск ценой измеримой нагрузки
  на человека.
- G-6: обратный эффект Кондорсе — независимое большинство соглашательских
  судей пропускает 27/32 дефектов, это хуже одного судьи.
- G-7: чтобы оценить долю пропуска судьи с точностью ±0,1 при ~95%, нужно не
  меньше 97 размеченных дефектов (нормальное приближение, худший случай
  p = 1/2).
- G-8: чтобы при нуле наблюдённых пропусков показать, что панель пропускает
  не больше 1% дефектов (95%), нужно 299 дефектных элементов; для 5% — 59
  (точное «правило трёх»). Калибровку на одного судью (G-7) это не заменяет.
- G-9: допустимая корреляция для целевого пропуска 1/10 у оптимистичных
  судей ρ* = 23/48 ≈ 0,48; при ρ* правило с эскалацией даёт ровно 1/10.
- G-10: пропуск дефекта большинством не зависит от доли ложных отклонений
  (1/10 или 1/25); при пропуске судьи меньше половины большинство лучше
  одного судьи.

**2. Проверки документа и реестра.**
- В `sources.json` нет дублей ID и URL; все URL — https; у каждой записи есть
  непустые цитаты, булев `verified` и известная позиция (stance).
- У каждой из гипотез H1–H8 не меньше пяти стресс-тестов с вердиктом.
- Каждый внешний URL отчёта есть в реестре.
- Каждый цитируемый ID вида `[A01]` (вместе с `aliases`) есть в реестре.
- Каждый источник реестра процитирован в тексте.
- Каждая строка таблицы §5.2 отчёта совпадает с моделью до трёх знаков
  (не меньше шести строк).

Параметры модели — иллюстративные допущения, а не измерения конкретных
моделей. Значения ρ и доли пропуска для реальной панели должна измерить
задача B-317 на размеченном наборе.

## Запуск и результат

Из корня репозитория. Нужен Python 3 и только стандартная библиотека:

```bash
python3 -I research/hub/exp/digital-employee-757/measure.py --check
```

Запуск не использует сеть, LLM, SDK или рекурсию. При исходном замере для
процесса был задан лимит виртуальной памяти 256 MiB (`ulimit -v 262144` в
Bash). В CI выполняется тот же `--check`.

`results.json` хранит:
- допущения модели;
- полную таблицу из 24 строк (2 профиля × 4 значения ρ × 3 правила);
- результаты 10/10 probes;
- SHA-256 `sources.json`;
- сводку проверок документа.

Сводка проверок документа:
- 141 источник, из них 137 подтверждены цитатой со страницы первоисточника
  или её архивной копии;
- 50 стресс-тестов по восьми гипотезам;
- все внешние URL отчёта есть в реестре;
- шесть строк таблицы §5.2 совпадают с моделью;
- неизвестных цитируемых ID нет;
- непроцитированных источников нет.

Это проверка арифметики и целостности свидетельств. Она не измеряет качество
LLM-судей.

Обычная проверка не меняет записанный результат. Чтобы намеренно пересмотреть
источники, текст или модель, есть режим `--write`. Полученный diff и
изменения выводов нужно проверить отдельно:

```bash
python3 -I research/hub/exp/digital-employee-757/measure.py --write
```

## Источники и границы воспроизводимости

В `sources.json` для каждого источника записаны:
- ID;
- название и автор или организация;
- дата или версия;
- URL;
- дата доступа;
- 1–3 дословные цитаты;
- краткий вывод;
- позиция к гипотезам: `supports`, `contradicts`, `conditional` или `context`;
- признак `verified` и способ проверки в `verification_note`.

Источники с одинаковым URL объединены, а их прежние ID сохранены в `aliases`.
Полные тексты источников не копируются.

Четыре источника помечены `verified: false`:
- C05 и C05b — пресс-релизы Gartner. Сайт отвечал 403, поэтому цитаты взяты
  из пересказа ITPro и из поисковой выдачи.
- C10f — релиз Amelia. Страницы вендора недоступны, цитата взята из
  перепечатки.
- E11b — блог Shingo Institute. Цитата получена извлечением моделью, а не
  побайтовым копированием.

Ни на один из этих четырёх источников вывод отчёта не опирается единственно.

Страницы McKinsey сверены с копиями Common Crawl. Отчёт MIT NANDA прочитан по
PDF с зеркала. Динамические страницы вендоров (цены, лендинги) не являются
immutable snapshot. Для репозиториев экосистемы (aether-orbis, ba-ai-metamodel,
hive-mind) записан HEAD на дату доступа; это чтение README и PR, а не аудит
кода.
