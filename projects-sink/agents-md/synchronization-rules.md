# Правила синхронизации `AGENTS.md`

## Источники и приоритет

| Слой | Источник | Действие |
| --- | --- | --- |
| Структура и инварианты | [стандарт бутстрапа](../../standards/agents-md-bootstrap-standard.md) | Сохранить обязательные секции, frontmatter, размер и единую точку входа. |
| Решение | [ADR-012](../../docs/adr/2026-09-adr-012-agents-md-root-contract.md) | Сохранить general layer и модель «канон + тонкий адаптер». |
| Архетип | `templates/htom/AGENTS.md` или `templates/spoke/AGENTS.md` | Выбрать по `.hub-profile.json`, не по названию репозитория. |
| Среда | `.hub-profile.json` и [таблица сред](environment-specific.md) | Добавить только объявленную дельту среды. |
| Проект | concept, README, локальные governance и artifact map | Заполнить только `<project_specific_rules>` и проектные маршруты. |

`derived_from` — provenance синхронизации, а не замена правила. B-111 должен
хранить проверяемую ссылку на точный upstream commit в машинно читаемом
профиле/манифесте проекта, например `derived_from.agents_md`, и не добавлять
неразрешённое поле во frontmatter `AGENTS.md`. Пока схема поля не принята,
upstream SHA фиксируется в PR, а не выдумывается в `.hub-profile.json`.

## Классификация правил

### Обязательное для каждого проекта

- одна корневая точка входа `/AGENTS.md`;
- frontmatter и полный список XML-секций из стандарта;
- general layer: `<hard_rules>`, `<forbidden>`, `<guidelines>` и
  `<hybrid_work>` без ослабления, удаления или локального переписывания;
- абсолютные URL на правила Хаба из spoke;
- human-in-control, issue → PR → review, validation и escalation;
- правило: модельные/средовые файлы являются только generated pointers.

### Адаптируемое

- `archetype` и `environment` — строго из `.hub-profile.json`;
- формулировки в `<scope>`, `<artifact_homes>`, `<context_scope>` и
  `<validation>` — под реальные дома и команды проекта;
- `<project_specific_rules>` — аддитивная дельта из принятого concept и
  локальных контрактов; она не может ослаблять general layer;
- `<routing>` — абсолютные Hub URL плюс существующие локальные маршруты;
- название, дата и ссылки — без незаменённых placeholders.

### Добавляемое только по доказанному условию

- адаптер среды — когда среда объявлена в профиле;
- локальный validator или command — когда он существует в репозитории;
- маршрут к локальной базе знаний — когда такой canonical artifact существует;
- проектное правило — когда оно выведено из принятого локального контракта, а
  не из поведения одного инструмента или текущей задачи.

## Процесс

### 1. Проверка

1. Прочитать issue, комментарии, README/concept и локальные governance.
2. Проверить наличие и согласованность `.hub-profile.json`: `archetype`,
   `environment`, `secondary_environments`, `project_specific_directories`.
3. Если профиля нет или среда не определена, остановить **только средовую
   адаптацию**: создать базовый профиль отдельным изменением или эскалировать;
   не угадывать GigaCode по файлам IDE. Cursor/Copilot adapters включать только
   по явному scope задачи или bootstrap-контракта.
4. Зафиксировать upstream SHA источника и текущее состояние project file.

### 2. Сравнение

Сравнить по секциям, а не целиком: frontmatter; обязательные секции; general
layer; архетипная дельта; средовая дельта; проектная дельта; adapters. Отчёт
классифицирует каждое изменение как `add`, `update`, `keep`, `remove-duplicate`
или `conflict` и показывает источник решения.

### 3. Адаптация

1. Взять текущий template нужного архетипа.
2. Перенести general layer без смысловых изменений.
3. Заполнить адаптируемые секции фактами из проекта.
4. Сохранить уникальные локальные правила только в
   `<project_specific_rules>`; конфликт с general layer вынести в PR.
5. Создать/обновить только требуемые [адаптеры среды](environment-specific.md).
6. Удалить дубли норм из adapters, сохранив generated pointer.

### 4. Валидация

- нет placeholders, относительных ссылок на Hub и второго SSOT;
- frontmatter и обязательные секции проходят validator стандарта;
- значения профиля совпадают с `<scope>`;
- размер: warning после 4K и fail после 8K tokens;
- локальные validators проекта зелёные;
- повторный dry-run B-111 даёт пустую дельту;
- PR содержит upstream SHA, delta report, решения `conflict` и остаточные риски.

Красная проверка останавливает merge, но не разрешает обход или ослабление
general layer.

## Обновление при изменении Хаба

Изменение корневого `AGENTS.md`, bootstrap standard или архетипного template
создаёт новый пользовательский цикл синхронизации. B-111 сравнивает записанный
`derived_from` с новым upstream SHA, формирует дельту и не перезаписывает
локальный файл без review. Проектная дельта переоценивается только если новый
general layer вступает с ней в конфликт.
