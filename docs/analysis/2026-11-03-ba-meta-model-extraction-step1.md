# Шаг 1 RFC #715: вынос проекта метамодели БА — имя, процесс, архетип, состав

## Summary / BLUF

1. **Имя.** Рекомендуется **`ba-ai-metamodel`**. Из 14 проверенных
   имён у четырёх нет похожих (поиск GitHub `in:name` по токенам даёт 0
   репозиториев), и только `ba-ai-metamodel` при этом точно называет
   содержимое: `universal-…` утверждает непроверенное свойство, а `gra-…` и
   `aether-orbis-ba` несут чужой или брендовый префикс. Дословных совпадений
   у него нет ни на GitHub, GitLab, Codeberg, Hugging Face, PyPI, npm, ни в
   вебе.
   Имя называет то, что делает проект отличимым (инвариантное ядро метамодели),
   и образует пару с `mango-ba-ai-runtime`: источник → поставка.
   Запасной вариант — `ba-ai-process`: сохраняет идентичность ADR-017, но
   делит токены с 282 репозиториями и совпадает с общей фразой «AI-процесс
   БА». Вариант `gra-…` не нужен: свободные имена есть, а GRA в экосистеме
   уже означает Gravity Reputation Architecture.
2. **Процесс владельца из трёх шагов подтверждён с четырьмя поправками.**
   (а) Перед постановкой задачи источники в Хабе замораживаются, а задача
   закрепляет коммит Хаба `HUB_SHA`. (б) «Чек-лист» — исполнимый контракт, в
   котором байты переносит инструмент, а агент только классифицирует остатки.
   (в) Копирование идёт шестью этапами E1–E6, по одному PR на этап, каждый с
   машинным доказательством. (г) Удаление в Хабе начинается только после
   этапа E6, отдельными задачами Хаба, и сначала переводит закрепление
   `mango-ba-ai-runtime` на коммит нового репозитория.
3. **Q-2: архетип B подтверждён**, критических противоречий нет. Два
   некритичных устранены в контракте: обзор `docs/ba-meta-model-overview.md`
   лежит вне каталога проекта (перенесён отдельной строкой `MAP`), а у проекта
   нет базового для B каталога `prompts/` (его роль играют
   `ba-meta-model/` и `dist/`, они задекларированы).
4. **Утверждение о составе — подтверждено как «база, а не закрытый объём», с
   тремя поправками.** «39 классов» не входят в выносимый Source: это
   стандарты `mango_ba_prompts` (draft 0.2.1), связанные с метамоделью
   проектным соответствием. «Фреймворк оценки» сегодня — Golden Set, гейт
   `G-mach` и метрики `M-1`…`M-5` одного MVP-среза, общего фреймворка нет.
   «Модернизация модели без модернизации практик» возможна только через
   версионированное соответствие (crosswalk) и раздельные оси версий.
5. **Контракт** — [`ops/hub-project-extraction-contract.md`](../../ops/hub-project-extraction-contract.md)
   с инструментом [`tools/spoke-extraction.py`](../../tools/spoke-extraction.py).
   Он не содержит имени репозитория и прорепетирован на реальных данных:
   322 файла, 231 коммит, 490 + 64 ссылки, 100 строк бэклога, расхождений 0.
6. **Вынос отложен владельцем 2026-11-04, имя согласовано.** Создан
   [`ba-ai-metamodel`](https://github.com/G-Ivan-A/ba-ai-metamodel); вынос
   (Ш3.0–Ш3.7) ждёт окна заморозки, потому что источник БА в Хабе меняется
   вместе с активной работой над `mango_ba_prompts` и `mango-ba-ai-runtime`.
   Стратегия — «пакет сохранён, запуск отложен»: всё, что нужно для выноса,
   сливается в Хаб и воспроизводится с `c06075d`, а возобновление начинается
   со сверки нового снимка дрейфа с базовым. См. «Отложенный вынос».

   структура и перенос данных, без имени репозитория и без посторонних
   постановок. Контракт должен устранять галлюцинации копирования.
4. Проверить Q-2 и утверждение о составе.
5. Записать решения владельца в RFC, реестр и бэклог; подготовить Хаб

Критерии и их применение:

1. **Нет дублей и похожих имён.** Дословно свободны все имена, кроме
   `ai-ba-playbooks`. Различимость отделяет кандидатов: у `ba-ai-process` и
   `ba-ai-framework` по 265–282 репозитория с теми же токенами, поэтому поиск
   по имени выдаст проект в длинном списке чужих.
2. **Индустриальная читаемость.** Имена GitHub — строчные слова через дефис,
   называющие предмет. «Metamodel» — устоявшийся термин моделирования (спецификации OMG MOF и
   UML пишут его одним словом); слитное написание даёт 0 соседей против 3 у `meta-model`.
3. **Согласованность экосистемы.** Последовательность `ba-ai` совпадает с
   `mango-ba-ai-runtime`; пара `ba-ai-metamodel` → `mango-ba-ai-runtime`
   читается как Source → Distribution ADR-017 без бренда в имени источника
   (Q-1 RFC: «архитектура поставки универсальна, `mango-only` — область
   содержимого»).
4. **Точность.** Ядро репозитория — каноническая метамодель
   (`ba-meta-model/`: 11 сущностей, закон производства `MM-1`…`MM-4`,
   33 навыка и 31 операция); компиляторы, дистрибутивы и тесты производны от
   неё. Владелец сам называет проект «Source-проект по БА мета модели».

**Почему RFC рекомендовал `ba-ai-process`, а анализ — нет.** RFC #715 (Q-1)
выбирал имя по непрерывности идентичности ADR-017 и `path_migrations`. Issue
#717 добавила критерий различимости, и по нему `ba-ai-process` проигрывает.
Цена смены имени мала: путь в Хабе меняется при выносе в любом случае, запись
`path_migrations` указывает URL нового репозитория независимо от имени, а
ADR-017 остаётся записью решения о проекте, а не об имени репозитория.

**`universal-…` и `gra-…`.** Первое имя утверждает универсальность, которая
не проверена: содержимое проекта — `scope: mango-only`, а ниже показано, что
универсальность требует ещё crosswalk и раздельных версий. Второе — запасной
вариант владельца на случай отсутствия свободных имён; свободные есть, а
[`aether-orbis-gra`](https://github.com/G-Ivan-A/aether-orbis-gra) определяет
GRA как Gravity Reputation Architecture, и префикс связал бы методологию БА с
репутационной методологией.

Ограничение: зонд проверяет имена репозиториев и пакетов, а не товарные знаки.
Codeberg отвечал 504 на 7 из 14 имён (отмечено в журнале); для
рекомендованного `ba-ai-metamodel` ответ получен — совпадений нет.

### Процесс выноса: проверка трёх шагов владельца

Вердикт: **подтверждён, с четырьмя поправками.** Простой перенос из Хаба
невозможен по тем же причинам, по которым возникают галлюцинации копирования:
агент, переносящий 322 файла из контекста, воспроизводит текст по памяти,
читает плавающий `main` и подтверждает результат словами. Прецедент —
`aether-orbis-gra` (проверка 8 RFC #715): Хаб не знал о выносе, появилась
третья форма `last_sync`, геном перенёс корневые `AI_*.md`.

| Шаг владельца | Подтверждение | Поправка и причина |
| --- | --- | --- |
| 1. Создать репозиторий | ✅ | Пустой репозиторий с начальным `README.md`; контракт сам разворачивает геном на этапе E1. Шаблоны GitHub и ручные файлы не нужны: иначе геном и импорт пересекутся |
| 2. Задача в новом репозитории на копирование по чек-листу в Хабе | ✅ | (а) До постановки задачи источники замораживаются, а задача закрепляет `HUB_SHA`: иначе два запуска дают разный результат (I-3). (б) Чек-лист — исполнимый контракт: файлы, история, ссылки и строки бэклога переносит `tools/spoke-extraction.py`, а агент классифицирует только строки `scan` этапа E4. (в) Шесть этапов E1–E6, один PR на этап, каждое число подтверждено файлом в `docs/import/hub-<sha12>/` |
| 3. Удалить или архивировать в Хабе отдельной задачей | ✅ | (г) Только после E6 и в порядке Ш3.5 → Ш3.6 → Ш3.7: сначала `mango-ba-ai-runtime` переходит на коммит нового репозитория, затем Хаб удаляет рабочие копии, оставляет надгробие (`path_migrations`, строки карт, переписанные входящие ссылки) и проверяет CI. «Архивирование» здесь — история git и надгробие; второй копии в Хабе не остаётся |

Опровергнуто одно допущение: что копирование можно проверить чек-листом,
который читает агент. Проверяемы только факты, которые выдаёт машина: хеши
файлов (`verify`), идемпотентность переписывания (`--check`), равенство
разделов бэклога (`sections --check`), подмножество расхождений (`adapted.txt`).

### Контракт выноса

[`ops/hub-project-extraction-contract.md`](../../ops/hub-project-extraction-contract.md)
— исполнимый документ (🚦, `executable: true`), который агент нового
репозитория исполняет по ссылке на закреплённый коммит Хаба. Все значения —
в блоке `extraction-params` задачи; в контракте нет имени репозитория, его
источников и ссылок на этот анализ.

| Причина галлюцинации | Правило контракта |
| --- | --- |
| Агент пишет файлы по памяти | «Байты — командой»: `materialize`, `git filter-repo`, `rewrite-links`, `sections`; ручная правка — только строки `scan` на E4 |
| Плавающий источник | «Один закреплённый коммит»: всё читается через `HUB_SHA`, инструмент тоже (`git show "$HUB_SHA:tools/spoke-extraction.py"`); заморозка проверяется в начале каждого этапа |
| Пути и значения выдуманы | «Один источник значений»: только блок параметров; манифест сверяется с журналом побайтно (`cmp`) |
| Успех заявлен словами | «Утверждение — с доказательством»: каждое число — файл в `docs/import/` |
| Расхождение «исправлено» агентом | «Расхождение — вопрос»: ненулевой код останавливает этап и задаёт вопрос владельцу |
| Переписаны записи решений | «Запись решения неизменна»: префиксы `HISTORICAL` не правятся; ссылки в них переписывает только инструмент по правилам L1/L2 |

Инструмент покрыт тестом [`tools/test-spoke-extraction.sh`](../../tools/test-spoke-extraction.sh)
в CI Хаба, поэтому контракт не устаревает молча.

**Отношение к [`templates/sync-project-with-hub-prompt.md`](../../templates/sync-project-with-hub-prompt.md).**
Это промпт сверки существующей спицы с Хабом и отчёта о расхождениях; он не
переносит данные проекта. Контракт выноса не заменяет и не дублирует его:
после E6 новая спица синхронизируется обычным путём (Ш2.4, Ш2.6).

### Состав как база масштабирования

Утверждение владельца: «Ядро мета-модели, компиляторы, универсальные
стандарты промптов (те самые 39 классов), фреймворки оценки (eval) — только
база для масштабирования, так как универсальность процессов может потребовать
модернизации модели без модернизации практик».

Вердикт: **подтверждено как направление («база, а не закрытый объём»), с
тремя поправками к составу и одним условием реализуемости.**

| Элемент | Факт | Вывод |
| --- | --- | --- |
| Ядро метамодели | `ba-meta-model/`: 11 сущностей, `MM-1`…`MM-4`, 4 таксономии, 33 навыка, 31 операция, `DP-1`…`DP-5`, `LG-1`…`LG-6`, `SK-0`…`SK-10` | ✅ Входит; это инвариант репозитория |
| Компиляторы | `build/compile-*-package.py`, `build/compiler/compile-product-taxonomies.py` с `--check` и `--source-revision` | ✅ Входят |
| «39 классов» | 39 стандартов `К-01`…`К-39` лежат в `mango_ba_prompts` (`standards/bcreq-manual-classes/`, draft 0.2.1, «статус всех новых правил — проект»). Сама спица пишет: «31 операция, 33 навыка L3 и 39 локальных классов относятся к разным множествам» и связывает их проектным соответствием | ❌ Поправка 1: не входят в выносимый Source и не универсальны. Остаются в `mango_ba_prompts` (Q-3, референсная реализация) |
| «Фреймворки оценки» | Golden Set, машинный гейт `G-mach`, метрики `M-1`…`M-5` вертикального MVP-среза, детерминированная эмуляция графа в `tests/execution-package/` | ⚠️ Поправка 2: это оценка одного среза, а не фреймворк. Общий фреймворк оценки — пробел, отдельная строка бэклога |
| «Модель без практик» | Компиляторы перегенерируют `dist/` из модели (`--check` в CI), `mango-ba-ai-runtime` закрепляет `source_commit`, 39 классов связаны соответствием без версии | ⚠️ Поправка 3 и условие: см. ниже |

**Почему модернизация модели без модернизации практик возможна, но не
сейчас.** Практики (39 классов, прогоны, пакеты runtime) не меняются при
изменении модели, только если между ними стоит версионированный интерфейс.
Сегодня он есть у одной связи из трёх:

1. Модель → runtime: ✅ `compilation-manifest.yaml` закрепляет коммит
   источника; runtime обновляется по своему решению.
2. Модель → `dist/` внутри репозитория: это намеренно жёсткая связь
   (дистрибутив — порождённый артефакт), практики здесь не «модернизируются»,
   а перекомпилируются.
3. Модель → 39 классов `mango_ba_prompts`: ❌ соответствие без версии модели;
   сама спица рекомендует «versioned crosswalk» с тремя ID и one-to-many
   (`2026-10-30-meta-model.md`, пункт 5).

Рекомендуемые действия: (1) версионированный crosswalk «операция/навык
метамодели ↔ класс практики» с диапазоном совместимых версий модели — в новом
репозитории; (2) ADR об осях версий: версия модели, версия crosswalk, версия
дистрибутива и `source_commit` runtime изменяются независимо;
(3) общий фреймворк оценки — после двух проектов-потребителей, не раньше
(иначе он обобщит один MVP-срез).

### Отложенный вынос (решение владельца 2026-11-04)

**Почему откладывается.** Контракт выноса требует, чтобы источники не
менялись в Хабе от закрепления `HUB_SHA` до надгробия (Ш3.6): иначе новый
репозиторий и Хаб станут двумя SSOT одного проекта, а шаг 0 контракта
остановит исполнение. Окно заморозки длинное — шесть PR этапов E1–E6 в новом
репозитории и три задачи Хаба Ш3.5–Ш3.7. Работа, которая в этот период меняет
источник БА в Хабе, уже идёт:

| --- | --- | --- |
| Хаб | [#719](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/issues/719) «ХАБ-1»: привязка `c-in.atomic_function` к каталогу продуктов и компиляция в `mango-ba-ai-runtime`; [PR #720](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/pull/720) меняет `projects/ba-ai-process/` | открыты, PR — WIP |

с одним `README.md` — это предусловие этапа E2. Всё, что устаревает, —
параметры и числа; поэтому сохранено не число, а команда и её вывод:
