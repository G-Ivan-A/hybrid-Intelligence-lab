# Выбор независимого спринта техдолга Хаба (issue #723)

## Summary / BLUF

Рекомендуется **Спринт 23 «Синхронизация производных контрактов ADR-021»**
(B-196, B-197). Из открытых спринтов Хаба он единственный, который сразу
готов к исполнению и никак не связан с тремя репозиториями экосистемы. Его
файлы есть только в Хабе. Ни одна спица не читает их при прогоне CI: спицы
закреплены на своих SHA Хаба (`3bfa410` у `mango_ba_prompts`, `32b5fa5` у
`aether-orbis-gra`), а у `mango-ba-ai-runtime` профиля синка нет. Ни один
открытый PR этих файлов не трогает. Решение по спринту уже принято: ADR-021
§4–5 и Agent Work Rules. Поэтому цепочки «Анализ → RFC» и «ADR → Стандарт →
Контракт» не нужны. Спринт реализуется одним PR в режиме Structured с
регрессионными тестами.

Повторная проверка нашла, что B-197 сформулирован уже, чем дефект. Режим
`Structured` по умолчанию задаёт не только handover-промпт, но и
`templates/htom/AI_GOVERNANCE.md`, и HTOM-шаблон issue. Рекомендуется
расширить B-197 без нового ID.

Порядок RFC #715 ставит техдолг последним (шаг 7). Для Спринта 23 его
причина (дублирующиеся ID, устаревший порядок) не действует. Поэтому
исполнение сейчас предлагается как зафиксированное точечное исключение,
которое утверждает владелец. Реализация в этом PR **не начата**, issue
требует ждать комментария владельца.

### Нужна ли цепочка

| Цепочка | Когда нужна | Применимо к Спринту 23 |
| --- | --- | --- |
| Анализ → RFC | Варианты открыты и нужно решение, которое затрагивает несколько контрактов | Нет. Анализ есть (2026-09-28 и этот документ), решение принято в ADR-021 |
| ADR → Стандарт → Контракт (промпт) | Нужна новая норма, а затем её отражение в стандарте и исполнимом промпте | Нет. Норма есть (ADR-021 §4–5, Agent Work Rules, протокол онбординга). Валидатор и геном — последнее звено «Контракт» уже существующей цепочки, и это звено отстаёт |
| **Прямая реализация (Structured)** | Принятое решение нужно довести до производных артефактов | **Да.** Один PR, регрессионные тесты, без новых норм |

Цепочка понадобится только в одном случае: если владелец выберет вариант,
противоречащий ADR-021, то есть оставит жёсткий 9K (Q-3) или `Structured` по
умолчанию для HTOM (Q-4). Тогда первым звеном будет новая ADR.

### Апелляция: порядок RFC #715

- **Норма.** RFC #715, шаг 7: «исполнять бэклог до нормализации (Ш6.3) и
  переприоритизации (Ш6.4) значит работать по дублирующимся ID и устаревшему
  порядку». В Спринте 30 записано: «Пока вынос отложен, порядок RFC действует
  без исключения: шаг 2 идёт первым».
- **Противоречие.** Issue #723 — более позднее прямое указание владельца:
  закрыть техдолг, не дожидаясь шагов 2–6.
- **Позиция исполнителя.** Причина последнего места к Спринту 23 не
  относится. B-196 и B-197 не дублируются, по ID не конфликтуют. Ш6.4 не
  может их закрыть как `CANCELLED`, потому что они исполняют принятую ADR.
  Ни один шаг 2–6 их не поглощает. Ожидание оставляет действующее
  противоречие в геноме, который получает каждая новая спица.
- **Предложение.** Записать исключение у строк Спринта 23 одной фразой со
  ссылкой на issue #723. Остальной порядок RFC не меняется. Альтернатива:
  отказаться от исключения и ждать B-261 (Q-1).

### Industry Practice Alert

Не применяется. Запрос владельца соответствует практике. Короткие
изолированные исправления дрейфа конфигурации относительно принятого решения
(config drift remediation) делают сразу и маленькими партиями, не дожидаясь
общей переприоритизации, если они не конкурируют за общий ресурс и не
дублируют другие задачи. Обе проверки выполнены выше. Практике
противоречил бы запуск спринта, который зависит от спиц или от
нормализации ID. Такие спринты матрица отклоняет.

4. **B-196, формулировки.** В строке `check-agent-work-rules-size.sh` файла `ops/artifact-map.md` заменить
